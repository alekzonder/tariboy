Desktop web UI

React and xterm.js provide the Desktop control surface while host-local daemons remain API and WebSocket services.

The main UI is a React single-page application under ui/src, loaded by the Tauri host in desktop/src-tauri. It talks to a selected local or remote tariboyd over HTTP and WebSocket. Daemons expose API/WS only and do not embed or serve the Desktop UI.

npm run build:desktop writes the SPA to ignored desktop/dist. make desktop always rebuilds it before Tauri packaging, so this output must never be staged. The separate store UI builds from ui/store into committed internal/storeui/dist and is served only by tariboy-store.

npm run build:android builds the same SPA for the Android app with VITE_TARIBOY_SHELL=android. In that mode isDesktop() is false, so servers use the browser registry (localStorage metadata, sessionStorage tokens) and no native command is called. The implicit same-origin “This daemon (local)” host is absent, the router is HashRouter, the daemon banner is hidden, an empty start screen offers Add server, and the server dialog accepts https:// or plain http:// to a loopback port only. A web link navigates the WebView, and the Android host’s navigation guard cancels that without waiting for the system browser. A background task opens the browser, so the navigation callback does not block the Android UI thread. If the browser cannot open the link, the current screen stays in place and the host logs a fixed message without the URL or error details. The app shows no failure message for this native attempt (see Security and controls). See Remote hosts.

Linux native UI verification uses make desktop-e2e: Playwright specs speak a small W3C WebDriver client through tauri-driver to a real debug Tauri/WebKit executable. The harness uses fresh owner-only daemon and Desktop state, rejects the live listener, and owns all driver/display cleanup. This complements the fast browser fixtures; it does not replace them and does not build Linux package artifacts.

Tauri creates one visible main window and opens the SPA directly. Daemon adoption/start and saved-host reconnect continue independently in the background, so their existing status banners may be visible during startup. Dock reopen and the menu-bar Open action raise the same main window.

Application settings live at /app-settings and remain available without a daemon connection; Settings → Application opens them. Desktop update checks use the native application host and never target the selected local or remote daemon. The settings screen, update status, and ready banner use English labels. Automatic download is enabled by default, persists in WebView localStorage, runs on startup and then every six hours while enabled, and never installs automatically. A verified package stays only in Rust process memory, so quitting Desktop discards it. When one is ready, the route-independent banner below the titlebar requires an explicit install action and reports installation failures for retry.

There is no interface mode. Every user gets the same agent workspace, and it uses progressive disclosure: the everyday views are tabs, and the rarer views are one step away. Mailbox and Advanced are routes that the agent’s Settings links to, the terminal hotkeys are behind Keys, and the header’s rarer actions are in its ⋯ menu. A value that an older release stored under app:ui-mode:v1 is ignored.

The New agent dialog shows five fields in this order: Run on (only when the workspace has more than one host), Folder, Image, Coding tool, and Name. One Advanced disclosure holds every other field. The dialog and the first-run card on the home screen (see First run) are one component, ui/src/pages/terminals/create-agent/NewAgentForm.tsx, driven by useCreateAgentForm. Ordinary creation starts with the documented defaults and submits one complete create request; the daemon writes one complete stopped agent row. A new agent opens on its Terminal tab.

  • Folder is the agent’s working directory on the selected host, with path autocomplete. It is required. Advanced → Folder → Use a managed folder clears it and sends an empty cwd, so the daemon makes a managed workdir.
  • Image lists one row per image name, with the newest built tag selected. Each row shows the name, the newest image_version, and the source when the daemon knows it. Typing filters by name. basic is first and selected by default, the other names follow in A–Z order, and bare is last as Plain terminal (bare). Advanced → Image → version picks another tag. When the host has no built image except bare, the host’s checklist rows are shown above the field.
  • Coding tool is a radio group from the host’s harness detection (GET /api/onboarding), labeled with the harness ID, for example Claude Code · claude. stub is never offered. The form selects the image’s default harness when it is found on the host, else the first found tool in the order Claude Code, Codex, OpenCode, Cursor. When the image declares no harness, the request carries that detected harness instead of an empty value. A tool that is not found stays selectable, shows its install hint, and blocks Start agent. A daemon without the onboarding route shows all four tools without found marks and blocks nothing. The field is hidden for a bare image.
  • Name is suggested as <folder basename>-<image name>, or <image name> for a managed folder, made unique against the host’s agents with -2, -3, and so on. The suggestion follows the folder and the image until you type a name.

Advanced has these groups: Identity (alias, team, color, notes), Image (version, plugins), Folder (managed folder, environment), Coding tool (Headless (no terminal), off by default), Autopilot (interval, soft and hard timeouts, timeout and error policies, idle limit, AI inactivity timeout, message batch and queue limits, standing prompt), and Tasks (the Goal settings), then Create without starting. Environment is a string-valued JSON object, schema-v1 plugins remain editable, and schema-v2 plugins are image-owned and read-only. Bare images are always interactive. There is no separate loop switch: Create without starting decides whether the new agent starts, and the footer button reads Start agent or Create agent. Interactive starts on for every new agent and selecting an image does not change it; the manifest’s harness.interactive is not applied. Clone mode copies the source agent’s value.

Ordinary creation defaults the soft iteration timeout to 7,200 seconds (2 hours) and the hard timeout to 10,800 seconds (3 hours). Clone mode continues to copy both timeout values from the source agent.

Agent creation, clone, and the agent’s Settings carry the per-agent Goal settings: an enabled-by-default switch, a positive whole-second customer-wait timeout (300 by default), and a positive Goal delivery cooldown (60 seconds by default). Settings shows the daemon-selected goal key read-only. While the agent works, the header sentence names that key. A question-mark action in the Settings Advanced → Goal section explains the sticky selection and release rules. The former server-global policy screen is not part of Settings.

Right-clicking any grouped or individual sidebar agent exposes Clone. Clone loads the source inspect projection from that agent’s explicit host, suggests a free name, and prefills every persisted agent-row configuration field, including raw configured CWD and message limits. Clone mode uses the same layout with Advanced open, so every copied field is visible. It does not copy secrets, history, runtime evidence, messages, subscriptions, scripts, workdir contents, retention, or budgets. The target host and image remain editable, and every follow-up request stays pinned to that explicit target. Older daemons that do not expose the complete clone projection must be updated. Starting the agent remains a separate retryable lifecycle request after creation.

The daemon rejects a folder that does not exist with bad_cwd, so a typo never creates a stray directory. 300 ms after you stop typing, the form lists the parent folder on the selected host with GET /api/fs/list. If the last part of the path is not in that listing, the field shows This folder does not exist. Create it. The link makes the create request send create_cwd: true, and the daemon makes the directory and its parents (mode 0755, owned by the daemon user) before it validates the path. A path that exists as a file still fails. If the parent cannot be listed, the form shows no link. A clone always starts without create_cwd.

While Start agent is disabled, the footer names the first unmet condition next to it: the source configuration, the target host’s image list, an unselected or unbuilt image, the starter image that the daemon still makes, the image manifest still loading, an empty folder, or a coding tool that is not installed on the host. A failed manifest load stays visible until the host or image changes, and Retry image loads it again. While the daemon still connects the catalog or builds basic, only basic waits: the image list shows it with the waiting reason, and Plain terminal (bare) starts at once.

Model and effort are shown as one line under the coding tool, for example Model: opus · Effort: medium. change opens the two fields. They are editable preset fields: they start from explicit runtime defaults for schema-v2 images and accept arbitrary values. Their suggestions come in two labeled groups. From harness holds the catalog the selected host returns from GET /api/harnesses/{type}/models (see Harness model catalog); it shows a loading note, the host’s error, or a note that an older daemon does not list models instead of failing. When the chosen model carries its own efforts (Codex), the effort field offers those, otherwise the harness-wide list. Saved holds the values the operator entered earlier for that harness, the current value, and the image default, minus anything already listed under the harness. Schema-v1 image defaults remain readable for compatibility. Successful creates and successful Settings Model saves remember the model and effort in the Desktop WebView by harness; failed ones do not add values. Neither group validates a value: an unsupported model still fails at the harness.

Shell and sidebar

The titlebar has the sidebar toggle, the product name, one search field, the ? (Help) menu, and the theme toggle. It has no settings gear, no workspace dropdown, and no view switch. The content island shows only the open object’s own tabs: there is no server bar above it.

The search field filters the agent list in the sidebar as you type. It also opens a result list with matching agents and matching tasks of every host in the workspace. Tasks match by key or title, open or closed: the lookup sends GET /api/tasks?text=…&status_view=all&limit=8 to each host 250 ms after the last key. A host that fails adds no results and shows no error. Enter opens the first result. ⌘K or Ctrl+K focuses the field. On a compact screen the field is at the top of the navigation drawer instead.

Tasks shows the number of tasks that need you, and Inbox shows the number of your open letters. A task needs you when its waiting_on is customer and it is not in its workflow’s initial status (workflow_initial), or when its waiting_on is pause (needsYouTask in ui/src/lib/needsYou.ts). A task that waits on a script, or that is in the initial customer status (for example backlog), never counts. The Tasks count is the number of distinct task keys on the hosts that answered: a task counts when needsYouTask selects it or when it has an open task.question letter, and it counts once. One read serves the two counts, Home, Inbox, and the agent states below: it reads each workspace host’s active task list, GET /api/mail/unread, and the Inbox box at the sidebar’s poll interval (3 seconds, or 15 seconds while the agent state socket is live). A host that does not answer adds nothing. When no host answers, the counts are hidden.

The agent list under Agents is open by default; the WebView remembers it in terminals:sidebar-agents:v1. It starts with a New agent button and the pinned agents. A row’s context menu pins and unpins it, and the WebView remembers the pinned set in terminals:sidebar-pinned:v1. A pinned agent shows only in the pinned block. Then each host lists its expandable Teams and its Individual agents. With one host in the workspace the list has no host heading. With two or more, each host has a heading with its reachability, an Update action when it runs an older daemon, and a ⋯ menu (Edit host, Remove host). A host heading opens /tasks?host=<id>.

An agent row shows the agent’s derived state (see Agent state). The dot has the color of the state. On the right, the row shows one pill: needs you · n in the accent color, working · 12 min with a clock that moves each minute, error in the danger color with the reason in its tooltip, or a muted off. An idle row shows no pill. The row has no other state, budget, or unread-letter badge; an open question is in Inbox and its task is in Tasks.

The foot of the sidebar is one line about the workspace’s hosts: Local · ready, 2 hosts · ready, or 2 hosts · 1 unreachable, with a dot when a host can be updated. The line opens Settings → Hosts, which holds Add host, Update all (N), and the host workspaces. Update all asks you to confirm the named hosts first. Then it runs the same host update on each of them in turn. If a host fails, the page error line names it, and the other hosts are still updated.

Host headings, team headings, and agent rows are themselves pointer- and keyboard-accessible drag surfaces; no separate drag handle is rendered. A drop reorders only like siblings, so it never changes team membership. The daemon stores each host’s team and agent order in the versioned sidebar_order_v1 value under daemon_config; missing or newly created names retain their current stable order. The Desktop WebView stores the cross-host order, including the implicit local host, in terminals:server-order:v1. Failed daemon writes restore the previous order and report the failure. Settings → Teams owns team creation and editing: arbitrary custom members, per-member runtime fields, rename/lead and membership controls, compose clipboard transfer, and portable archive import/export. All requests retain the active explicit host, including raw archive uploads and downloads.

Routes and host scope

/tasks, /inbox, /activity, the Library pages, and the Settings pages other than Hosts show one host. They take an optional ?host=<id> (local is the local daemon). Without it, the page shows the remembered active host. A ?host= that names another host selects it through the route host boundary, which shows Connecting to host… or Host unavailable. while it does. With two or more hosts in the workspace, the page has a host selector, and a pick replaces ?host=. Settings → Hosts and Settings → Application have no selector. With one host nothing about hosts is shown, and links that the UI builds carry ?host= only with two or more hosts. A desktop notification always names its host.

Home

/ is Home when the workspace has at least one agent (ui/src/pages/home/HomePage.tsx, loaded on first open). It has a New agent button and four sections:

  • Needs you (N): the tasks that need you on every workspace host, newest first, then your open letters. A question letter about a listed task is not shown again. A task row opens the task drawer on its host, and a letter row opens /inbox?letter=<id>. The chevron button Answer in place before a task row expands the row into its Needs you card, so you can answer without the drawer. With nothing to show it says Nothing needs you. When no host could be read, it shows the error and Retry.
  • Running now (N): the agents in state running, with the time since current_iteration_started_at. Each row opens the agent’s Terminal.
  • Today: the Activity totals of the page host for the last 24 hours, with History, which opens the Activity table at /activity.
  • Recent: eight agents, newest last_iteration_at first; agents that never ran follow in sidebar order.

First run

While every host of the workspace has zero agents, / shows the first-run home (ui/src/pages/terminals/FirstRunHome.tsx) instead of Home. It has a welcome line, the Getting ready checklist, the inline Run your first agent card, and the line Later: connect another computer over SSH in Settings. As soon as any host has an agent, / shows Home. A dead agent route, an empty workspace other than the default one, and a workspace with no host keep their own empty states.

The checklist shows the host selected in the card’s Run on, which is the first host by default. It reads GET /api/onboarding through useOnboardingStatus and has three rows:

  • the Tariboy catalog: connected, connecting, could not connect, or removed (add it again in Library → Sources);
  • the starter image basic: ready (also when an image named basic already existed), building, or could not build;
  • the coding tool: which harnesses the host found and which it did not, with their install hints. When no tool is found, the row is a warning.

The hook polls every 5 seconds while a row can still change by itself (the catalog is pending, or the starter image is pending or building) and stops when every row is final. A failed row shows one sentence, a Details disclosure with the raw daemon error, and Retry, which calls POST /api/onboarding/retry and starts polling again. A daemon without the onboarding route (older than this release) gives no status, so the checklist is hidden. The rules are pure functions in ui/src/lib/onboarding/firstRun.ts.

A missing coding tool is never a red banner. The daemon still counts “at least one agent harness” among its missing tools, but the daemon banner removes that entry: when it is the only missing tool there is no banner, and when other tools are missing the banner names only those. A host added later shows its checklist inside the New agent dialog, when it has no built image except bare, and on its Stores page.

After create, the agent opens on Terminal. Above the terminal, one banner line always says what the screen shows (see Agent terminal), for example Starting Claude Code in ~/code/my-app… while the coding tool starts, or Claude Code did not start: and the reason, with Retry (start the agent and reconnect the terminal) and Open settings. Without a session, the terminal says No terminal session. Start the agent, or turn on Interactive terminal in Settings → Autopilot. Below 1200 px, the agent header puts its buttons on their own row under the sentence.

Onboarding

The onboarding tour explains the work process on the screen itself. Each step dims the window, puts a ring around one element, and shows a card with a short English text, a counter such as 4 of 12, and Skip tour, Back, and Next (Done on the last step). The arrow keys move between steps, and Esc closes the tour. While the tour is open, clicks on the dimmed interface do not pass. The tour shows where an action is, but it does not open dialogs or create objects.

The steps go through the screen in this order: Welcome, Agents, the agent workspace, the agent’s Settings tab, the sidebar’s Tasks item, the sidebar’s Library item (images), the Library’s Sources tab, the hosts line at the foot of the sidebar, Add host on Settings → Hosts, the Filters menu of Tasks (queues), the Library’s Workflows tab, and the ? (Help) button. The Agents step goes to / and highlights the New agent button of Home, or Start agent on the first-run card; it never highlights the sidebar’s New agent button. A step with a route opens that page through navPath in ui/src/lib/navRoutes.ts: tasks and inbox open /tasks and /inbox, and the Library items open /library/images, /library/sources, and /library/workflows on the active host, and settings opens /settings/hosts. The agent steps open the first agent of the sidebar. If the sidebar has no agent row when the tour starts, the tour leaves out the agent steps, and the counter counts only the steps it shows (1 of 10). Done, Skip tour, and Esc go back to the route where the tour started. If the sidebar is hidden on a wide window, a sidebar step shows it. On a phone width, the sidebar is a modal drawer that takes focus from the card, so the tour closes the drawer, and the sidebar steps show their card in the center. A step whose element is not on the screen, or has no size, also shows the card in the center without a ring. The tour checks for the element every 100 ms, so the ring follows the element after a route change, a resize, or a scroll.

The agent workspace step says “Work, Terminal, Activity and Settings of one agent: …”. The agent settings step says “Settings sets the coding tool, model, working folder, Autopilot and spending limit. Everything else is under Advanced.” Its ring is on the Settings tab link.

ui/src/lib/onboarding/tour.ts holds the steps and TOUR_ANCHORS, the data-tour values. A component marks an element with data-tour={TOUR_ANCHORS.name}, and a step names the same constant, so a step cannot name an anchor that does not exist. tour.test.ts also checks that a component uses each anchor that a step names. The steps whose element moved to the sidebar shell carry since: "0.101.0" and updated: true, so What’s new shows them after that release. The version of the UI comes from scripts/release-version.txt, which scripts/set-version.sh writes at release time.

onboarding:state:v1 stores the version whose tour the user finished or skipped. The full tour never starts by itself. These rules apply at start:

  • No version is stored: the UI stores the UI version, as if the tour were done, and nothing starts.
  • The stored version is older than the UI version, and a step has a since value after the stored version, up to the UI version: What’s new starts. It shows only those steps, with a New mark, or Updated for a step with updated: true, and a Full changelog link.
  • Otherwise, the tour does not start, and the stored version moves to the UI version.

Skip tour, Esc, and Done store the UI version. Take the tour does nothing while a red daemon banner (data-daemon-banner="error") is on the screen, and a toast says The tour opens after the daemon error is fixed.

Three one-line hints replace the automatic tour. Each is shown once per agent until you dismiss it:

  • Terminal: “Type what you want done. To hand work over and let the agent run on its own, give it a task.”
  • Work: “Tasks you create here are given to this agent.”
  • Settings: “Autopilot: choose whether the agent also runs every few minutes on its own. Everything else is optional.”

A dismissal is stored under onboarding:hint:v1:<host>:<agent>:<tab>, where <tab> is console, work, or settings. Dismissals that an older release stored under tasks or configuration are not migrated, so those two hints show once more. If the storage is blocked, a dismissed hint comes back after a reload.

The ? menu in the titlebar, and the Help card in Application settings, have Take the tour, What’s new, and Changelog. What’s new from the menu shows the steps whose since is the UI version. If no step has that value, it opens the changelog. The Changelog window shows CHANGELOG.md of this UI build: the versions on the left and the text of the selected version on the right. It shows the changes of the running UI, not of a remote daemon. If the file has no ## [VERSION] - DATE headings, the window shows the whole file. When Full changelog opens it, the versions after the stored version have a New mark.

The Vite configurations allow the dev server to read the repository root (ui/vite.fsAllow.ts), because the UI imports CHANGELOG.md and the version file with ?raw. The default deny list of Vite still applies.

Activity

An agent’s Activity tab and the host Activity page (/activity, opened by History on Home) use one period bar with different periods. The host page offers Hour, Day (the default), Week, and Custom. The agent tab offers Today (from local midnight until now, the default), Week, Month (30 days), and Custom; a URL with hour or day, such as a link from the host page, still works there. Hour, Day, Week, and Month are rolling windows that end now and move once a minute. Custom takes a start and an optional end as local times; without an end it runs to now, and a missing or reversed range shows an error in the period bar. The period and the selected view live in the URL query (?period=hour|day|today|week|month|custom, ?since=/?until= for Custom, ?view=), so a view is shareable and survives a reload; a change replaces the history entry.

In labels an iteration is a run: the cards, the table headers, and the views say Runs. API and URL names keep iteration.

Under the period bar, the host page has six cards that total the work on tasks in the period: tasks, completed tasks, status changes, comments, runs, and cost. The agent tab has four: Tasks done, Runs, Cost, and Avg. cost per task (— when no task completed). They come from one GET /api/task-activity?since=&until=[&agent=] response (ttasks activity), polled every 10 seconds; a response for an older period or host never replaces the current one. The daemon builds it from AI requests tagged with a task and from task events in the window: per task the iterations, requests, tokens, and cost, the comments, the outcomes an agent declared, the workflow statuses the task entered, whether it completed, and the first and last activity. With agent only that agent’s requests and events count; without it the response also breaks the period down per agent. AI requests without a task do not appear here; they stay visible in the Runs log and Usage. Tasks the caller cannot see, and tasks removed by maintenance, are left out. One response lists at most 500 tasks, most recent first, and says so; the totals still count every task.

The agent tab is one view for every user. Under the cards it shows:

  • the per-task table: one row per task, newest activity first. The task key opens the task panel in place, over the Activity tab; the tab and the URL do not change;
  • the cost chart for the period, from getAgentUsage;
  • a More segment with three views:
    • Runs log (default): the iteration audit view, the same component as Advanced → Full audit, limited to runs that started in the period, with the tag filter below;
    • Usage: the agent’s AI usage over the period; task and epic keys open the task panel in place;
    • Status history: only the status messages from the period.

An old ?view=iterations, ?view=usage, or ?view=status link opens the matching More view, and an old ?iteration= link opens the Runs log. The host page has a Tasks view with an Agents column, whose keys open the task panel in place on that server, and an Agents view, whose names open that agent’s Activity tab with the same period. All its requests go to the selected host.

The agent’s Settings, Activity, and Advanced pages and the server Activity page share one frame, TabPage: 16 px side and top padding, 24 px bottom padding, and 16 px between blocks. Settings is a centered column of at most max-w-5xl; the others use the full width. Mailbox, Work, and Terminal fill the page without a frame.

Iteration tags in Activity

The Runs log filters its iteration list by tag. API layer

ui/src/lib/api/ is the only HTTP client of the Desktop UI. @/lib/api resolves to its index.ts, which assembles the client and re-exports the modules; it holds no requests of its own.

  • client.ts owns the transport: JSON requests that unwrap the {ok, result} / {ok, error} envelope, raw requests for archives, uploads and text exports, and the single ApiError class (status, code, message, details). Every request uses cache: "no-store", sends the host’s bearer token, and passes the caller’s AbortSignal. A JSON GET that gets no complete response in 30 seconds fails with network_error and the message request timed out, so a connection that never answers cannot stop a refresh loop. Writes and raw requests have no time limit.
  • lib/resume.ts calls its listeners when the page becomes visible again or the browser comes back online. On that event the tasks, mail and agent state WebSockets and the agent event stream close and open again at once, and the shared query client rereads its active queries. A WebView can keep a socket open after its connection stopped, for example after an Android port forward dropped.
  • hosts.ts owns server selection: the active host that the host switcher sets, the local daemon origin that Desktop sets at boot, and the ApiTarget type (undefined = the active host, null = the local daemon, a Daemon = that host).
  • One module per domain: agents, iterations, usage, daemon, harnesses, plugins, scripts, files, images, imageSources, groups, stores, mail, audit, tasks, and workflows. Each module re-exports the types of its responses (see API types) and exports a factory that receives a transport bound to one host. Domain methods never take a target. lib/tasks.ts and lib/audit.ts keep only presentation helpers.
  • mail.ts is the mailbox client: list, show, send, reply, close, read, requeue, unread, and clear (an agent’s inbox). Each call takes an optional as, the principal it acts as; without it the daemon acts as the customer. lib/letters.ts holds letterTaskKey(letter), the string data.task_key of a letter or "", apart from the client so the shell’s eager modules can read a letter without loading it.

createApi(target) returns an ApiClient: the bound transport plus one section per domain, such as api.tasks.getTask(key) or api.images.listImages(). The target is fixed when the client is created: undefined resolves to the active host once, and a later host switch never redirects an existing client. A registered host without an endpoint (an SSH tunnel that is reconnecting) yields a client whose ready is false; its requests fail with host_not_ready and never fall back to the local daemon.

React code reads the client from context:

const api = useApi()
const detail = await api.tasks.getTask(taskKey, signal)

ApiProvider fixes the server for the tree below it. DaemonProvider provides the active host, RouteHostBoundary provides the route host, and an agent workspace, a server pane, or a dialog with its own host picker mounts a provider for that host. Components do not pass a target down to children. useApi() outside a provider throws, and component tests render through @/test/queryRender or the apiWrapper / fakeApi helpers in @/test/api.tsx. An equal target keeps the same client across renders, so effects and subscriptions that depend on api do not restart. A new endpoint or token for the same host gives a new client without changing any tree key: loaded data and unsaved drafts survive a reconnect, while requests and subscriptions move to the new connection. A response from the previous client never replaces data of the current one.

Code that works with several hosts at once creates one client per host with createApi(daemon): the all-hosts agent list, the all-servers task view, and customer question notifications. A transfer between hosts (a task, an image, a workflow image) holds one source client and one destination client for the whole operation. The native host registry, SSH tunnels, and Keychain tokens stay in lib/daemons.ts and lib/desktop.ts.

API types

ui/src/lib/api-types.generated.ts holds the TypeScript types of every response that /api/openapi.json describes. npm run api-types in ui/ generates it from the committed snapshot internal/commands/testdata/openapi.json, and the ui-api-types step of make frontend-check fails when the file is out of date. Do not edit it; see Go control plane and plugins for the workflow after an API change.

Each schema is a top-level type with the Go type’s name, such as AgentRow or TaskDetail. A domain module re-exports the types that its callers need, for example export type { AgentRow, AgentView } from "../api-types.generated", and components import them from @/lib/api. Comment and Event would shadow DOM globals, so tasks.ts re-exports them as TaskComment and TaskEvent. Where the spec has a plain string and the UI needs a union, the module narrows it at one place, such as taskPriority(task).

The types follow the spec exactly. A list that Go can return as null is T[] | null, and an optional field is optional, so the code handles both. Test data is a complete response, not a partial literal; the factories in ui/src/test/fixtures/apiFixtures.ts fill the fields a test does not check.

These types stay hand-written. Each response type among them has a comment that says why the spec does not cover it:

  • Responses that internal/api/server.go serves outside the command registry: the agent event stream (AgentEvent), the tasks WebSocket frame (TaskEventHint), the mail WebSocket frame (MailHint), the operations WebSocket frame (OperationHint), and the image, team, and workflow image archive imports.
  • The transcript calls of audit.ts, which the spec describes only as objects.
  • Request bodies and filters, such as CreateAgentSpec and TaskFilters, and types that the UI derives, such as AgentPromptLayer.

Code splitting

The first download contains only the shell: the titlebar with the search field, the sidebar navigation and agent list, the hosts line, the “needs you” context, the providers, host selection, and the agent workspace frame. Everything else loads with React.lazy when it first renders:

  • the pages in TerminalsRoutes (Home, Tasks, Inbox, Activity, Images, Workflows, Sources, and Settings), the host selector, and the nested image and settings routes of routes.tsx;
  • NeedsYouLive, which reads the counts and rows of “needs you”, the task lookup of the search field, and the workspace manager dialog;
  • every agent workspace tab and the Goal task drawer in AgentWorkspace;
  • the Needs you card (tasks/NeedsYouCard.tsx) in the Work tab and in the Home list, because it brings the Markdown renderer;
  • the TipTap editor (tasks/TaskMarkdownEditor.tsx): MarkdownEditor in TaskMarkdown.tsx is a lazy wrapper, so MarkdownContent never loads TipTap;
  • the file viewer of FileBrowser, with CodeMirror, its languages, and the highlighted preview;
  • the onboarding tour overlay and the Changelog window with CHANGELOG.md. The shell keeps only the ? menu, the steps, and the version check.

components/LazyBoundary wraps each place that renders a lazy component. It sits inside the layout that stays mounted, so the titlebar, the sidebar, and the settings navigation stay visible. While a chunk downloads, the content area shows a role="status" text, Loading…. A later open uses the loaded module. A navigation inside the router is a transition, so the previous screen stays until the next one is ready. If a chunk fails to load, for example after an update or when the server is unreachable, the boundary shows This screen failed to load. and Reloading discards unsaved input. with a Reload button. It never retries by itself. A new route path, tab, or file clears the error.

vite.desktop.config.ts puts vendor libraries in named chunks with build.rolldownOptions.output.codeSplitting.groups, the Vite 8 replacement for manualChunks: react (React, React DOM, and the router), codemirror, tiptap (TipTap and ProseMirror), xterm, and markdown (react-markdown, remark, rehype, and highlight.js). One more group, api, holds the app’s own HTTP client (src/lib/api/, lib/daemons.ts, and lib/storage.ts): the shell and most lazy screens share it, and without the group the bundler folds it into the entry chunk once enough screens share it. Only react and api are part of the first download; each other group loads with the first screen that needs it. Keep a group narrow: if the shell imports one module of a group, the whole group becomes part of the first download.

npm run bundle:budget, a step of make frontend-check, has three limits in bytes before compression. The entry chunk is limited to 351,000 bytes. The entry chunk plus its static imports is limited to 723,000 bytes. All JavaScript chunks, lazily loaded ones included, are limited to 3,215,000 bytes. The step fails when a size is over its limit. The budget does not measure CSS or the start time on a device.

WebView storage

ui/src/lib/storage.ts owns all access to localStorage and sessionStorage in the Desktop UI and the Store UI. It declares every key in one registry with its area, name, version, parser, and fallback value. Other modules call readKey, writeKey, and removeKey with a key from that registry. The unit test ui/src/test/webStoragePolicy.test.ts fails when production code under ui/src or ui/store uses localStorage, sessionStorage, or window.dispatchEvent directly. It scans the sources because the lint policy allows no per-file oxlint overrides. Tests and fixtures still seed raw values, so they detect a change of a stored format.

Storage access is best effort. A missing value, a value the parser rejects, broken JSON, and storage that throws (blocked, private mode) all read as the fallback value. A failed write returns false and does not throw, so the interface keeps its state in memory until a reload. A read that finds a bad value does not delete it; the next write replaces it. Values are never logged, because some of them are tokens.

Key names did not change when the registry was added, so saved state survives upgrades. A new key uses the form <area>:<purpose>:v<N>, and the registry test requires a versioned name to end with its version. When a format changes incompatibly, the key gets a new name with the next version. The old name stays in the registry only so it can be read once, like terminals:workspace:v1. A key that nothing reads any more leaves the registry; its old value stays in the WebView unread. This is the case for terminals:sidebar-tab:v1 (the former Servers and Agents tabs), app:ui-mode:v1 (the former interface mode), and the session key tasks:all-view:v1 (the former All tasks view).

TanStack Query v5 owns the server data for Tasks. One QueryClient serves the application, and each component test uses an isolated client. List keys include the agent scope, text, status view, assignee, and waiting principal. Queue filtering remains local. History keys distinguish the workspace’s latest 200 events from the drawer’s first 200 events.

Queries read the server from the surrounding ApiProvider; a client for the local daemon has the identity local. Server identity is independent of its endpoint. A new SSH port cancels old reads and refreshes active queries without changing their keys or form state. An unavailable endpoint disables background reads. Credentials never appear in query keys, logs, or persistent storage. Credential changes clear that server’s old data, and removing a host removes its cached queries.

The cache holds data only in memory. Inactive queries expire after five minutes. Data is stale immediately, so reopening a view refreshes it in the background. Automatic retries, window-focus refresh, and browser reconnect refresh are disabled. The host connection adapter controls reconnect reads. When the page becomes visible again or the browser comes back online, the client rereads all active queries once (see API layer). Network failures retain a loaded snapshot. A 401 or 403 response clears the server’s cached data and shows the access error.

HTTP responses remain authoritative. The task socket opens after HTTP supplies its starting sequence. The event adapter combines a burst into one refresh cycle per server and query client, including one notification read. Multiple subscribers deduplicate the same event sequence. An event during a cycle requests a trailing cycle. Socket frames never replace task records.

Writes cancel competing reads before and after the operation. They then invalidate the same server’s task queries, so lists, details, history, notifications, and workflows refresh together. An optimistic tree move restores the previous rows on failure and reads the server again. A rejected save keeps its draft, including after a revision conflict. Writes do not retry or queue for an offline host. WorkflowPanel owns workflow-action refreshes; its parent does not start a second cycle. A successful notification-read write cancels intervening inbox reads before updating the read marker. It marks the inbox stale for the next socket, manual, or mount refresh.

For another Tasks reader, reuse its typed query options:

const api = useApi()
const detail = useApiQuery(taskQueries.detail(api, taskKey))

Keep selection, drafts, expansion, sizing, and focus in the component. Pass the query’s AbortSignal through every paginated read. The shared layer discards cancelled results. New resources need keys for every response parameter.

Terminals, the aggregate task list, the attention coordinator, and standalone queue forms retain their existing loaders. Their migration belongs to separate work. The drawer opened from those screens already shares the Tasks queries. Specialized workflow actions and log readers retain their own state.

Agent workspace

Agent state

The sidebar row, the agent header, and the Terminal banner show one derived state. deriveAgentState in ui/src/lib/agentState.ts computes it in the UI. The first state that matches wins:

State When
error the agent state is error or failed, it has a halt_reason whose halt_kind is not idle_limit, it has an error_reason, or a budget is exhausted. The state carries the reason.
needs you · n n is more than 0 (see below)
working the agent state is running; the elapsed time starts at current_iteration_started_at
off the agent is disabled
idle any other case

n counts the agent’s tasks (assignee agent:<name>) that needsYouTask selects, plus the open task.question letters from agent:<name> about a task that is not already counted. One task counts once. A task that waits on a script, or that is in the initial customer status (for example backlog), never counts. An idle_limit halt is the loop stopping as configured, so it is not an error; the header shows its reason in muted text.

The data comes from the shared “needs you” read (NeedsYouLive and useNeedsYou) that also serves the sidebar counts and Home: each host’s active tasks and the user’s inbox, polled at the sidebar interval. The state adds no request per agent and no API change. A host that does not answer gives its agents no needs you pill.

The header has no state pill, host label, image chip, Goal link, working directory row, or budget line. Daily and monthly limits are in Settings → Spending limit. Hourly and weekly limits are under Advanced. Below 1200 px the sentence and the muted line wrap, and the buttons take a row of their own.

Work tab

The Work tab (ui/src/pages/agents/work/AgentWorkTab.tsx) has its own layout. It does not use the Tasks workspace, so it has no Active | Done | All segment, no Filters or Queue menu, no My tasks or Waiting for me, no agent chip, no Columns, no refresh button, and no tree or table columns. Top down, it shows:

  1. The composer (TaskComposer.tsx), one line with the placeholder “Give <agent> a task…”, a Give button, and Details.
  2. Needs you (n): one Needs you card for each item of the agent’s needs you state, the same items that the tab badge and the header count.
  3. In progress (n).
  4. Queued (n).
  5. Done · last 7 days (n), with a search box and Show all.

The composer works like this:

  • Enter, or Give, creates a task with the typed title and priority P2. Each create sends an idempotency key, so a retry after a lost response does not make a second task.
  • The queue is the one remembered for this agent in tasks:new-task-queue-by-agent:v1 (a JSON object from server to agent name to queue prefix) while that queue exists, else TASK. A create saves the queue in that record and in tasks:new-task-queue:v1.
  • Details reveals the queue, the priority, and a description editor.
  • For a flexible queue, the request sets the assignee to agent:<name>.
  • For a queue bound to a workflow, the request has no assignee, because the daemon refuses one (workflow_managed). The composer shows the note “Dispatched by the <name> workflow; a pool member takes it”. After the create it shows the line “<KEY> dispatched by the <name> workflow”, which opens the task drawer.
  • When the agent is off, the button reads Start & give. It creates the task and then starts the agent. If the start fails, the task stays and the composer shows the error.
  • When the agent’s Goal setting is off, the composer shows “Goal is off: this agent does not pick up tasks. Turn it on in Settings”, with a link to Settings. The create still works.

The rows come from listTasks with assignee=agent:<name>, one read with status_view=active and one with status_view=closed, through the shared task queries (useAgentWork.ts). The task event stream keeps them fresh. A task that a Needs you card shows is not repeated in the other sections. Queued holds the active tasks in the open category and the tasks in their workflow’s initial status (workflow_initial). In progress holds the other active tasks. Done holds the closed tasks of the last seven days. Show all shows every closed task in the same rows. The search box filters Done by key and title.

A row shows the key, the title, the status in words (statusWords in workModel.ts), the age, and the cost from the task activity report when it is known. The status words are “Not started” for a task in the initial status, “Waiting for you”, “Paused”, or “Waiting on a check” by waiting_on, else the workflow status humanised or the flexible label. A Queued row of a task in its workflow’s initial status has one button per item of its workflow_outcomes. The first outcome whose target is not terminal comes first, as the primary button. An outcome named start reads Start, and the others read “<outcome> → <status>”. A button sends the advance through useWorkflowAdvance.

A row click opens the task drawer. The tab reads these query parameters:

Query Effect
?task=KEY opens that task in the drawer
?answer=KEY scrolls to that task’s Needs you card and focuses it
?give=1 focuses the composer

Needs you card

NeedsYouCard (ui/src/pages/tasks/NeedsYouCard.tsx) is one component for three places: the Work tab, the top of the task drawer, and the Needs you list on Home and Inbox when a task row is expanded. The Work tab and the list load it lazily. The card shows:

  • the key, the title, the status in words, and the age;
  • the open question, as Markdown: an unresolved wait that addresses the customer and does not come from system:workflow;
  • for a customer status of a workflow, the sentence “<agent> waits for your decision in <status>.”, then the artifacts to review. These are the artifacts that the step into the status required, then the artifacts that its outcomes require, each with its latest value. Each artifact is collapsible, the first one is open, and the value renders as Markdown;
  • one Message box;
  • for a customer status, one button per outcome, labeled “<outcome> → <next status>”. A button whose outcome misses an artifact is disabled, and its title names the artifact. The advance carries the message and from, and goes through the useWorkflowAdvance hook, the same path as the Outcomes block of the workflow panel;
  • for an open question, Send answer and Reply Ok to the question. Both post a customer comment, which resolves the wait. Reply Ok to the question shows only while the message box is empty;
  • for a paused task, the pause reason with Continue, Release holder (pool status only), and Cancel task.

Host workspaces

A workspace is a named, independent list of registered hosts in one app window. Settings → Hosts has a Manage workspaces… button. When there are two or more workspaces, it also has a selector that lists them with a check on the current one, followed by New workspace… and Manage workspaces…. Choosing a workspace narrows the agent list, the hosts line, the search, the Tasks and Inbox counts, and Home to that workspace’s hosts, so an empty workspace shows no agents. Settings → Hosts stays open after the pick. Home of an empty workspace shows <name> has no agents yet with a Manage workspaces button. Polling continues for every host, so the manager can show each host as ready or offline, and agents on hosts outside the current workspace keep running: a workspace filters the window, it does not isolate hosts. Agents and tasks live on their daemon, so a host in two workspaces shows the same agents and tasks in both.

Default is built in and cannot be renamed or deleted. A host may belong to several workspaces. A host that no workspace lists, such as the local daemon or a host registered before workspaces existed, is in Default. Add host puts the new host in the current workspace only, for SSH and HTTPS alike; adding the same alias or URL again makes a second host entry. The manager dialog creates a workspace (Enter or Create workspace; blank names are ignored) and selects it, and renames a custom workspace as its name is typed without ever saving a blank one. Add to… and a click on a target workspace add a host there and keep it in the current one. Remove takes a host out of the selected workspace only; a host left in no workspace returns to Default, so the manager offers no Remove for a host that only Default holds. Delete workspace asks inline; its hosts in no other workspace return to Default, and deleting the current workspace switches to Default. Remove host in a host’s menu removes the host from the app and so from every workspace.

The state is the WebView localStorage record app:workspaces:v2: {version: 2, workspaces: [{id, name, hosts: [hostId]}], active}, where the first entry is Default. When it is missing, the version 1 record app:workspaces:v1 ({version: 1, workspaces: [{id, name}], hostWorkspace: {hostId: workspaceId}, active}) is read once: each host keeps its one workspace, and a host without an entry stays in Default. The version 1 record is left in place. The state is local to one app installation and is not stored by any daemon, because hosts are the set of daemons rather than something one daemon owns. Malformed or unavailable storage falls back to Default only; unavailable storage keeps changes until the window closes.

Switching agents and reconnects

The former All tasks view, one task table across every host, is removed. /tasks shows one host at a time, with a host selector when the workspace has two or more hosts, and an old ?view=all URL opens /tasks.

Selecting another agent in the sidebar while an agent workspace is open keeps the tab that is currently open and shows the new agent in it, so the same view answers the same question about the next agent. An unknown tab still falls back to Work, and a selected task in the ?task= query is dropped because it belongs to the agent being left. A sidebar agent selected from any other page opens on Work. A freshly created agent opens on Terminal. Start and Stop are in the agent header; the Terminal banner of an agent that is off also has a Start button.

When a known explicit server route temporarily loses its tunnel or its authoritative aggregate refresh fails, the Desktop retains its last successful server and agent snapshot in React memory rather than flashing the whole pane to an error. The live host badge and a local status message identify the unavailable/reconnecting state; that host’s agent controls and cached sidebar agent rows are read-only until a successful refresh for the same host replaces the snapshot atomically. Cached data is never persisted or used as an API target, other server navigation remains available, and a missing host still fails closed rather than falling back to local authority.

A reconnect never remounts a server page. An SSH host loses its endpoint while its tunnel reconnects and comes back on a new local port. Neither change is part of a page’s identity: Tasks, Workflows, Stores, the Settings pages and an agent’s Settings tab keep their loaded data, the open task, filters, scroll position and every unsaved draft. The route boundary keeps one tree shape and only dims the page and makes it inert under a single status line. A host object keeps its identity until one of its fields changes, so the sidebar poll does not restart page loads.

While the host has no endpoint, background loads are skipped rather than failed. When the new endpoint arrives, each page re-reads once in place: the task list, the open task, the agent header, the agent’s Settings and Mailbox. A background read that cannot reach the host (host_not_ready, network_error) keeps the last data and shows no toast, because the host header in the left panel already reports the host as offline with its error. An explicit action such as Save, Create or Send still reports its failure. Its draft stays in the form, ready to send again once the host is back. Drafts live in tab memory only and are not queued for later delivery.

The agent’s Settings tab has four groups in order:

  • Model: coding tool, model, and effort.
  • Working folder: the current path and Change…, available while the agent is stopped. The editor includes Create directory if missing.
  • Autopilot: Only when given tasks or messages, or Also every with an interval in minutes. Stop a run after sets the soft timeout in minutes, with 0 for no limit. Interactive terminal is here too.
  • Spending limit: daily and monthly USD limits, with the daemon’s current spend beside each. 0 means no limit.

Advanced starts collapsed. It contains Image, Schedule and timeouts, Goal, Mail, Hour and week budgets (USD), Environment, Retention and cleanup, and Other views. Schedule and timeouts holds the schedule builder, hard timeout in seconds, timeout and error policies, idle limit, and AI inactivity timeout. Its next scheduled start comes from the daemon and follows Save changes. A saved schedule can start runs even when Autopilot has no timer interval.

Below Advanced, About names the image and host. The image links to the Library. Danger contains Delete agent. Start, Stop, and Restart stay in the agent header and apply immediately.

Schedule is a builder for the agent’s RRULE (see Schedule). You select a mode and fill in its fields: None (no schedule), Every N minutes / hours, Daily (one time), Weekly (days and one time), Monthly (a day of the month or the last day, and one time), Once (a date and a time), or Custom RRULE (a text field for any rule). The builder shows a one-line summary and the rule it sends. Times are in the time zone of the daemon host, not of the browser. When the page loads a saved rule, the builder selects the mode that builds exactly that rule. If no mode does, for example a rule with two times or with UNTIL, it selects Custom RRULE and shows the rule unchanged. A rule you do not edit is not marked Changed. When you select another mode, the builder drops the saved DTSTART, and the daemon starts the new rule at the current minute.

Every editable field belongs to one page-wide draft. A field is dirty when its normalized draft differs from the value last loaded. The field shows Changed. A sticky header at the top lists the unsaved count and groups, with Reset and Save changes while edits exist. The Advanced disclosure also counts its unsaved edits. Closing it keeps those drafts. Reset drops every draft. Save changes first validates every changed field in the browser and sends nothing while any is invalid. It opens Advanced or the folder editor when needed and focuses the field. Then it sends only changed fields through the existing per-field endpoints. Requests run serially in the existing order, with harness before model and effort. The four budget limits and the two retention limits each save as one request. It stops at the first failure without sending the fields after it: acknowledged fields adopt the daemon’s canonical values after a reload, while the failed field (with the server’s reason beside it) and the ones never attempted stay dirty drafts, so the next Save sends only them. There is no batch endpoint, so a Save is not atomic. Harness and Interactive are saved with the page like every other field; they take effect the next time the agent starts and never restart it. Create directory if missing is saved with the working directory as one request: when it is on, Save sends the path with create: true, and the daemon makes a missing directory before it validates the path. After a successful Save the switch is off again.

For a stopped agent, the working directory is edited with the selected host’s directory autocomplete. Saving changes the CWD used by the next launch; it does not move files or start, stop, or restart the agent. Active agents show the current CWD read-only until they are stopped. Remote agent reads, directory suggestions, and saves all use the host identified by the agent route rather than whichever daemon was previously active. Refreshing live agent, image or host status does not replace an unsaved draft; the draft is discarded only when the agent or the host changes. The agent image is a draft field too; Copy digest, Cancel pending and Retry of a failed pending assignment stay immediate actions in an actions row that says they are not part of Save.

Model and effort use the same grouped suggestions as agent creation, for the agent’s host and the selected harness.

Advanced → Schedule and timeouts exposes the positive AI inactivity timeout in seconds, defaulting to 1800 (30 minutes) per agent. When a running iteration exceeds it without an attributed AI-proxy request, the daemon reports state=error, which the agent header shows. The controls remain enabled because this signal does not stop the loop or iteration; the next request restores state=running. Ordinary creation starts at 1800 seconds, while Clone preserves the source agent’s configured value.

The Advanced → Mail section uses that same draft contract for the positive whole-number messages_batch and messages_max_queue fields. New-agent drafts use a maximum queue of 100, while Clone keeps the source agent’s configured value.

Settings also renders the daemon-authoritative per-agent USD budget projection. The daily and monthly fields are in Spending limit. Hourly and weekly fields are under Advanced → Hour and week budgets (USD). Each pairs current spend with an editable limit, where zero means unlimited. All four limits save in one request against the explicit agent-route host. Older daemons that omit the projection show neither budget section. The agent state uses the same projection: an exhausted period makes the state error, with the reason Out of budget: and the exhausted periods. The header’s “$x today” also comes from it. The browser never recomputes spend. Older daemons simply omit the additive projection.

The workspace header also consumes daemon-authoritative message status. When messages_queue_full is true it displays Inbox full: pending / limit in destructive styling; it never recomputes queue state in the browser. The normal status refresh removes the indicator after processing or clearing lowers the queue.

When the daemon reports a halt reason for the agent, the header shows it on every tab, so a loop that stopped before any iteration existed (a failed image activation, for example) is visible. A halt whose halt_kind is not idle_limit makes the state error, and the reason is the header sentence in red. An idle_limit halt is not an error: its reason is a muted line under the sentence. Without a halt, an error_reason from the daemon is the error reason. The reason shows whether or not the agent is started, because a stop-policy, idle-limit, or launch-failure reason matters exactly when the loop is off.

The common agent list can be hidden and restored throughout the hierarchy. On macOS the main Tauri window retains native traffic lights under an overlay titlebar, and the sidebar icon is immediately after their reserved area in the global toolbar, followed by the product name. The search field, the ? menu, and the theme icon are the other titlebar controls. Empty toolbar space is draggable, while daemon status banners remain below the titlebar so they never cover the native controls. The shared persisted sidebar state drives both that control and the server/agent shell. Its width and hidden state persist in the WebView localStorage record terminals:sidebar:v1; the first read after upgrading adopts the sidebar saved by the removed terminal canvas under terminals:workspace:v1. The 72px gap kept for the traffic lights exists only in the Desktop app.

Compact screens

Below 1024 CSS pixels (Tailwind’s lg) the window is compact: phones and most tablets. Below 768 CSS pixels (Tailwind’s md, the DRAWER_QUERY of useMediaQuery) the agent list takes no room beside the island. The titlebar’s sidebar toggle becomes a Open menu button that opens the same sidebar as a drawer (Navigation) from the left, at most 85% of the width. The titlebar search field is hidden there, and the drawer has its own Search agents field at the top. The drawer opens without focus in Search agents, so a phone does not raise its keyboard; the first Tab moves focus into it. From 768 to 1023 CSS pixels the agent list stays a column, and the titlebar’s Hide agents / Show agents toggle collapses it as on a wide window, saved in terminals:sidebar:v1. Picking an item, an agent, a host or a team, New agent, Add host…, editing a host or cloning an agent closes it, and so do a tap outside, Escape, and any route change, Back included: the drawer belongs to the history entry it opened on. A window that grows past 768 CSS pixels drops it, so it does not come back when the tablet turns again. It has no resize handle and is never stored: the wide layout’s width and hidden state in terminals:sidebar:v1 stay as they were.

Other compact rules:

  • The agent header wraps instead of overflowing. The folder in the muted line is cut from the left with the full path in its tooltip, and the primary / Start or Stop / ⋯ buttons take a row of their own under the sentence, so they never cover it.
  • The agent tabs and the Settings navigation scroll sideways with no visible bar, and the current tab scrolls into view. The Settings navigation is a strip above the page instead of a column.
  • Below 640 CSS pixels (sm) the task table shows only Key, Task and Status at fixed widths, and the Columns menu, the column move grips and the resize handles are hidden. The saved column layout tasks:columns:v1 is not changed; priority stays in the task’s detail.
  • Dialogs keep a 16px margin on each side, and two-column dialogs and editors (the workspace manager, the image source editor) stack.

ui/tests/responsive.pw.ts checks these at 360×800, 390×844, 820×1180, 1024×700 and 1180×820 against an isolated daemon: no visible element may end past the right edge of the window unless it is inside its own horizontal scroller, the header controls must not cover the agent’s details, and the agent list must be a drawer exactly when the window is compact. At 1024 CSS pixels and wider, every toolbar marked data-toolbar on Tasks, Inbox, and the Library must keep its children on one row, and the sections of Home must not overlap. Toolbars move secondary controls into a menu instead of wrapping.

Send files, Attach, and terminal file drops all upload through the selected server’s streaming PUT /api/files/raw endpoint, with a 1 GiB per-file limit. The browser sends each File as the raw request body instead of building a base64/JSON copy. Uploads have no agent destination: files live in the server’s shared files directory and the returned absolute paths are inserted into the corresponding draft or reported when no terminal is available. Terminal retains its explicit host target.

Agent terminal

The agent Terminal tab mounts xterm.js and opens GET /api/agents/{name}/terminal. Binary WebSocket frames carry PTY bytes; text frames carry resize messages. A host or agent route change tears down the old socket and dials the newly selected target without stopping the tmux session.

One banner line above the terminal always has text. It follows the agent state and the terminal session:

Case Banner
error “<tool> did not start: <reason>”, with Retry and Open settings (…/settings)
not interactive “No interactive terminal. Enable it in Settings → Autopilot.”, with a link to …/settings; the drop target for files and Send files stay below
off “Off.”, with a Start button
starting “Starting <tool> in <cwd>…”
working “Working on <KEY> — this is its live screen.”
idle “Idle. The screen appears when a run starts. Type here to talk to the agent directly; this is not recorded in a task.”

Without a session, the terminal panel says “No terminal session. Start the agent, or turn on Interactive terminal in Settings → Autopilot.”

The toolbar under the terminal has Send files, Compose, Scrollback, a Keys toggle, and the ? help. Keys (with aria-expanded) shows or hides the hotkeys Esc, Enter, Ctrl-C, ↑, and ↓. Keys starts expanded in the Android build and collapsed in other builds. The help text starts with: “Terminal is for working with the agent by hand. For work it should carry out on its own, give it a task in Work; it runs it when it is on.”

In the Terminal tab, explicit http:// and https:// text in terminal output opens in the operator’s default browser on Command-click (the Meta modifier); this is a Desktop capability and does nothing in a plain browser. The Android app has no Command key, so there a tap on the link opens it. An ordinary click never opens anything and keeps xterm’s own focus, selection and mouse behaviour untouched. Nothing else is actionable: file paths, file://, javascript:, data:, custom schemes, protocol-relative and bare-host text are not even rendered as links, and the URL is parsed and its scheme re-checked natively before anything is launched — the terminal matcher and the WebView are not the authorization boundary. A link that cannot be opened reports a fixed message that never contains the terminal line.

The Terminal tab toolbar exposes Scrollback. It sends tmux’s own copy-mode entry sequence (prefix C-b, then [) over the existing byte socket, and the toolbar then shows a persistent Viewing scrollback status, Page back / Page forward controls, and an Exit scrollback button. Live keystrokes are paused while tmux is in copy-mode; press q in the focused terminal or use Exit scrollback to return to live output. Every control is a labelled button reachable by keyboard. Because the browser has no authoritative tmux mode event, the status describes the state Tariboy requested, not a verified tmux mode, and it is cleared whenever q is typed in the terminal, Exit scrollback is used, the socket closes, the terminal identity changes, the session becomes absent, or the tile unmounts — leaving copy-mode any other way still strands the status, notably via Escape, which cancels under tmux’s default emacs table (including from the toolbar’s own Esc hotkey) but only clears the selection under copy-mode-vi, so the browser cannot infer it. Entering and leaving scrollback are both announced through a status region that stays in the DOM either way — a live region that unmounts announces nothing — and leaving via Exit scrollback returns keyboard focus to the Scrollback control, while leaving with q keeps focus in the terminal. tmux mouse reporting stays off, so wheel and drag input continue to belong to the inner harness TUI.

What Scrollback browses is the tmux pane history, not xterm scrollback, and it is bounded: the shim sets each managed session’s history-limit to 10,000 lines (tmux’s own default is 2,000), so older output is discarded by tmux and cannot be recovered from the browser. Nothing about the history is persisted by the UI.

The agent header’s ⋯ menu has Run once…, only while the agent is enabled and not bare:latest, for interactive and non-interactive agents alike. It opens the Run once dialog, whose optional, memory-only one-shot text is sent to the route-selected host and affects only the newly requested iteration. Run once does not start the agent or persist the draft. A successful request closes the dialog and, when the Terminal tab shows an interactive terminal, reconnects its startup handling; a rejected request keeps the dialog and the draft for retry.

Settings → Danger → Delete agent opens an in-app confirmation dialog. It names the agent and warns that its durable data is also removed. Confirm sends the existing force=true and purge=true request. While that request is pending, the dialog cannot be dismissed or submitted again. The workspace returns home only after success; on failure it keeps the dialog open, restores its controls, and reports the error so the operator can retry. Force-stop current run in the ⋯ menu is a separate action. It asks for confirmation in an in-app dialog, stops only the current iteration or session, and does not delete the agent or its durable data.

An agent’s Advanced → Retention and cleanup section edits its override of the server-wide iteration defaults with the page Save: each field shows 0 = server default (N), and the block lists the effective limits and that pruned iterations are archived with their database rows first.

Secrets in Advanced → Environment are write-only. The section lists key names only. Removing a key and adding a key and value are page drafts applied by Save: a removal is shown as Will be removed until then, and a new value lives only in tab memory, is sent in a POST body and never in a URL, is never rendered, and is cleared once the daemon acknowledges it.

Preview cleanup and Prune now stay immediate actions outside Save. The in-app retention prune is guarded by a confirmation dialog that names the operation as permanently destructive and bounds it to the current retention policy. Confirming dismisses the dialog and issues the real, non-dry-run prune; while it is in flight the destructive action is disabled and cannot be issued twice. A failure is reported beside that action inside the bounded destructive section, not in the dialog, so the operator can read it and retry. Previewing what the policy would remove stays a separate, unconfirmed action.

Terminal connection outcomes are intentionally distinct:

  • 4404 is retried for a five-second startup grace because the agent engine and shim socket can become ready shortly after Start returns;
  • 1000/eof means the attached PTY ended and stops immediately;
  • abnormal transport closes retry with capped exponential delay while the view remains mounted.

The Desktop SSH host dialog also keeps transport connectivity separate from the result of the current provision or update operation. It maps native phases into six ordered user-facing steps and retains a failed update result even if rollback restores a healthy old tunnel. Native stdout and stderr events are bounded diagnostic output, not lifecycle results; only an explicit error event or a failed host runtime state terminates the operation. Raw process output is collapsed under Technical details, while the main flow renders one actionable error and one primary next action.

DaemonProvider also exposes daemon_status.app_version to both host-list surfaces. Their compact Update action is derived only from a confirmed mismatch between that bundle version and the non-empty persisted/runtime remote daemon version. Unknown versions fail closed without an update indicator; the host editor retains its explicit manual update action.
