This is the canonical development guide for the repository. `README.md` is the
short entry point; this page owns the detailed workflow, commands, safety rules,
and documentation routing.

## Before changing code

1. Read the user request or current task as the source of truth for scope.
2. Inspect `git status` and preserve unrelated work already in the tree.
3. Read this guide and the topical documents from
   [What to read for each task](#what-to-read-for-each-task).
4. Locate the existing tests and the nearest working implementation pattern.
5. Identify whether the change affects generated output, persisted state,
   security boundaries, remote hosts, or a running daemon.
6. For behavior changes and bug fixes, reproduce the behavior and add a
   regression test before changing production code.

The root `AGENTS.md` turns this workflow into repository instructions for coding
agents. `CLAUDE.md` contains additional rationale for the live-daemon and
generated-artifact safety rules.

## Prerequisites

The control plane requires **Go 1.26**. Use the repository lockfiles for Node
and npm dependencies.

Install only the toolchains needed for the area you are changing:

- **Go control plane:** Go 1.26, Make, a C toolchain where required by the host.
- **Fast checks:** ripgrep (`rg`) for the packaging secret-scan contract in
  `make backend-check` and `make check`. Install with `apt-get install ripgrep`
  on Ubuntu or `brew install ripgrep` on macOS; the PR workflow installs it.
- **React UI:** Node.js and npm.
- **Desktop native host:** Rust (minimum package version 1.77), Cargo, the Tauri
  prerequisites, and platform build tools.
- **macOS packaging:** Apple Silicon macOS 12+, Xcode command-line tools,
  `codesign`, `hdiutil`, and the other checks reported by `make desktop-mac`.
- **Agent smoke suites:** `tmux` is checked by both `make smoke` and
  `make full-smoke`; the latter adds the interactive terminal cases.
- **Documentation:** Node.js and npm.
- **Daemon host:** `tmux`, `bash`, `python3`, `git`, `npx` (Node.js), the
  `tariboy` and `ttasks` links in `~/.local/bin`, and at least one harness.
  `GET /api/daemon/status` reports `state: error` with the missing tools; see
  [Daemon host tools](/docs/remote-hosts#daemon-host-tools).

Coding agents run shell commands directly in their tool shell, which already
has the account's profile environment. Do not wrap a command that carries text
(a commit message, a pull request body, a task comment or an artifact) in an
extra `bash -c` or `bash -lc` layer: quotes, backticks and newlines in the text
break that layer. Write the text to a file with the Write tool and pass the
file (`git commit -F`, `gh pr create --body-file`, `ttasks ... --file`), or use
a quoted heredoc at the top level of the command. Keep credentials in the
environment; never print their values.

Load the Rust environment before Cargo or desktop commands:

```bash
. "$HOME/.cargo/env"
```

Do not assume a GUI-launched macOS application inherits the interactive shell's
`PATH`; native runtime dependencies must be handled at the Desktop process
boundary.

## Runtime PATH contract

At daemon startup, Tariboy defines the account baseline by invoking the
configured shell as an interactive login shell with a fixed internal probe:

```text
$SHELL -ilc <fixed Tariboy PATH probe>
```

The probe is not constructed from user input. It has a five-second timeout,
bounded combined output, disconnected stdin, and a machine-readable delimiter
so startup messages cannot be mistaken for the result. The daemon accepts only
an absolute executable shell and a non-empty result without NUL bytes, then
sets the resolved `PATH` before initializing agent, plugin, or HTTP services.

Desktop reads the effective macOS account's configured shell and supplies it
only to the daemon child. Direct terminal and SSH launches use their inherited
`SHELL`. Desktop's bootstrap path can locate the daemon and common host tools,
but it is not the final runtime path. If shell selection or the bounded probe
fails, daemon startup remains available with its inherited `PATH` and emits a
stable warning; neither the inherited nor resolved path nor shell startup
output may be logged, audited, or included in support bundles.

After resolving the account baseline, a packaged daemon prepends its shared
runtime `bin` directory, which contains a `ttasks` symlink to the sibling
`tariboy-tasks` payload. This makes the bundled client available to fresh
Desktop agents without the optional CLI installation. The alias is refreshed
atomically and retained across restart handoff.

The final iteration environment preserves this precedence:

1. daemon environment, including the resolved account baseline;
2. harness-required environment;
3. explicit agent environment and resolved secrets;
4. for non-bare images, the agent bin directory prepended to the resulting
   `PATH`.

An explicit agent `PATH` therefore intentionally replaces the daemon baseline
before non-bare agent-bin prefixing. Bare images receive no agent-bin prefix
but still inherit the daemon baseline unless the agent overrides it. Harness
shell wrappers use `/bin/sh -c`, not a second login shell, so they preserve the
already-resolved environment. The runner validates the selected harness
executable against this final environment before it starts the shim.
Schema-v2 image skills add only adapter-owned launch arguments or environment
entries. They may not override `HOME`, `CODEX_HOME`, or `XDG_CONFIG_HOME`.

## Build and verification matrix

Use the smallest fast entry point that covers the change; the aggregate and
heavy targets compose them:

```bash
make backend-check   # Go and smoke contracts
make frontend-check  # UI and documentation
make check           # both fast checks
make full-check      # heavy, tens of minutes, includes check
```

Run `make backend-check` for backend-only changes and `make frontend-check` for
frontend- or documentation-only changes. Run `make check` for mixed changes or
when ownership is unclear. The backend target runs `fmt-check`, `vet`,
`staticcheck`, `gocyclo`, `test`, Go unit tests and smoke contracts. Its
`test` and `tariboy-tasks-e2e` steps also check the HTTP API against the
committed OpenAPI snapshot; see [Go control plane and plugins](#go-control-plane-and-plugins). The
frontend target runs the UI format check, the generated API types check, UI
typecheck, lint with the complexity and size thresholds, the unused-code check, unit tests,
branding, the bundle budget, and the documentation checks. Before checking, `backend-check` runs `go mod download`
for the module and for `tools.mod`. `frontend-check` uses
`scripts/npm-ci-locked.sh` for locked installs under `ui/`, `ui/tools/api-types/`
and `docs/`.
They do not write into
`bin/` or dirty `git status`. Each step reports its result and duration as it
finishes.
Successful check-step output is suppressed; failed steps print their command
and complete diagnostics, and every run ends with a compact summary.

`make full-check` is the full set of checks that run unattended on a developer
machine, not every check in the repository. It runs `check`, then `build`, the
four core E2E scripts, `full-smoke`, the two Playwright browser suites, and one
desktop step for the host: `desktop-e2e` on Linux x86_64, `desktop` plus
`desktop-smoke` on macOS arm64, and the version and lock gates alone elsewhere.

After dependency preparation succeeds, the check steps do not stop at the
first failure. Each step is timed and recorded, and the run ends with a summary
table naming every step that failed, so one aggregate pass surfaces gofmt drift
and a UI type error together.

`frontend-check`, `check`, and `full-check` reuse dependencies when a saved
SHA-256 fingerprint matches `package.json`, `package-lock.json`, and the Node.js
and npm versions. A fingerprint identifies those inputs by their contents.
Missing or changed fingerprints trigger `npm ci --no-audit --no-fund`.
The script saves the fingerprint inside `node_modules` only after installation
succeeds. Checks still run on every invocation.

Use `TARIBOY_NPM_CI_FORCE=1 make check` to force both installs. Use this after
manual changes inside `node_modules` or changes to npm configuration, such as
`.npmrc` or install flags. Those changes are outside the fingerprint.
Deleting `node_modules` also forces installation on the next run.

Three scripts stay outside `full-check` deliberately and are run by hand:
`scripts/product-alpha-e2e.sh` and `scripts/remote-provision-smoke.sh` require a
disposable SSH host (the first also requires explicit consent to destroying its
data), and `scripts/check-alpha-artifacts.sh` is a release gate that takes a
release directory as its argument. The Rust host tests are outside both targets
as well; see [Rust desktop host](#rust-desktop-host).

The individual targets remain callable on their own, so running `make vet` or
`make e2e` while iterating is still legitimate. Use the smallest relevant
check, `make check` for mixed changes, and `make full-check` when the diff
reaches e2e, packaging, or desktop behavior.

## Cleaning the working tree

`make clean` runs `git clean -dfx`. It permanently removes every ignored and
non-ignored untracked file and directory in the repository, including build
output, caches, dependency directories, and other local-only files. It leaves
tracked files and tracked edits unchanged. Git's single-force protection also
leaves nested repositories and worktrees intact.

Preview the exact paths before deleting them when the working tree may contain
local files you still need:

```bash
git clean -ndx
```

### Go control plane and plugins

`make backend-check` covers this subsystem with `fmt-check`, `vet`,
`staticcheck`, `gocyclo`, and `test`. To run one of them from the repository
root while iterating:

```bash
make vet
make staticcheck
make gocyclo
make test
make fmt-check
```

Those targets enumerate the module's packages and exclude `node_modules`; a Go
fixture embedded in an npm dependency is not Tariboy source and must not extend
the Go quality gate.

The versions of `staticcheck` and `gocyclo` are pinned in `tools.mod` and
`tools.sum` at the repository root. This separate module file keeps the
dependencies of the linters out of `go.mod`. The targets run each tool with
`go tool -modfile=tools.mod NAME`, so you do not install anything into
`$GOPATH/bin`. To move a tool to a new version, run
`go get -modfile=tools.mod -tool PACKAGE@VERSION` and commit both files.

`make staticcheck` runs the default checks plus `ST1005`, as `staticcheck.conf`
sets, with `-tags=tmux`. Fix a new finding in the same change. If a finding
depends on separate work, disable only that check in `staticcheck.conf` with a
comment that names the task.

`make gocyclo` fails when a non-test function has a cyclomatic complexity
over `GOCYCLO_OVER` in the `Makefile`. The value is a ratchet: it is the
current maximum, and a change that simplifies the most complex function lowers
it. Do not raise it. The target for new code is 25. Test files are not
measured. `make gocyclo-report` prints the 30 most complex functions and the
average, and it never fails.

`make fmt` is not a check: it rewrites files. Only `fmt-check` is part of
`backend-check`; run `make fmt` yourself when it reports drift.

`make build` produces the core binaries. It is not part of `check`, which
writes nothing into `bin/`, and it is the first build step of `full-check`.
Optional external plugins have their own build under `plugins/`. Canonical
image sources, Agent Skills, and their static prompts are maintained in the
separate `tariboy-store` repository rather than embedded in the binaries.
`desktop-binaries` compiles the local and remote daemon payloads without
building an agent image.
`make install` installs the resulting commands under `$HOME/.local/bin`; it is
not required for normal unit-test work.

The Tasks mode E2E inside `backend-check` builds its five required binaries in
temporary directories, so the check never regenerates workspace `bin/`.

`make server-install` builds all six real server binaries, stages and verifies
their checksums, publishes a versioned release under
`$HOME/.local/lib/tariboy/<version>`, and transactionally switches the matching
`$HOME/.local/bin` links. `ttasks` is an additional alias for
`tariboy-tasks`. It does not start or restart the daemon.

Native Tasks changes normally need focused tests under `internal/tasks`, the
operator route/OpenAPI registry tests under `internal/commands`, and the agent
command contracts in the separate `tariboy-store` repository's `make check`.
Changes to queue-trigger delivery also exercise mail ingress and daemon recovery; Compose
changes exercise `internal/compose`. The isolated Tasks mode path is
`scripts/tariboy-tasks-e2e.sh`, which runs inside `backend-check`.

The HTTP API contract is checked inside `backend-check`; see
[Command registry](/docs/architecture#command-registry) for the rules. The
`test` step fails for a new HTTP command without a result schema, for a
response that does not match its schema, and for a spec change without an
updated snapshot. The `tariboy-tasks-e2e` step fails when the isolated daemon
serves a spec other than the snapshot or answers a typed `GET` route outside
its schema. The snapshot is `internal/commands/testdata/openapi.json`. A change
to a command's arguments, summary, route or result type changes the spec, so
update the snapshot in the same change:

```bash
go test ./internal/commands -run TestOpenAPISnapshot -update-openapi
```

Give every new HTTP command a typed result: a named struct, or a slice of
one, declared with `registry.WithResult`. A handler never returns
`map[string]any`; `TestHTTPCommandsDeclareResultSchema` and
`TestCommandsReturnNoRawMaps` fail otherwise. Add a call for the new operation
to `TestTypedResponsesMatchOpenAPI`: a domain registers its calls in
`typedCallSets` from an `init` function in its own test file. Before you
change a handler's result type, pin its JSON in the domain's golden test (for
example `daemon_golden_test.go`) on the unchanged handler, and keep that
golden file unchanged through the change.

The UI does not declare response types by hand. `ui/src/lib/api-types.generated.ts`
is generated from the snapshot and committed. After you update the snapshot,
regenerate the file and commit both in the same change:

```bash
cd ui
npm run api-types
```

The command reads the snapshot from the repository and needs no running
daemon. The `ui-api-types` step of `make frontend-check` runs
`npm run api-types:check`. It generates the file again in a temporary
directory and compares it with the committed file. When they differ, the step
fails, prints the diff and the command above, and changes no file. Fix the UI
code that the new types break: `npx tsc -b` names every place. See
[API types](/docs/architecture/web-ui#api-types) for how the UI uses the file.

The generator, `openapi-typescript`, runs from its own package in
`ui/tools/api-types/` with its own lock file. It needs the TypeScript 5
compiler API, and `ui/` uses TypeScript 7, so the two cannot share one
`package.json`. `frontend-check` installs the package with
`scripts/npm-ci-locked.sh` like `ui/` and `docs/`.

#### Changing an API response end to end

One pull request carries an API change from the Go type to the UI. For
example, to add a field to an agent response:

1. Add the field to the result struct in the domain's `*_types.go` file under
   `internal/commands`. If the change replaces the result type, first pin the
   current JSON in the domain's golden test, as described above.
2. Update the snapshot:
   `go test ./internal/commands -run TestOpenAPISnapshot -update-openapi`.
3. Regenerate the UI types: `cd ui && npm run api-types`.
4. Run `npx tsc -b` in `ui/` and fix every place it names. Add the new field
   to the factory in `ui/src/test/fixtures/apiFixtures.ts`, so test data stays
   a complete response.
5. Use the field in the UI through the domain module's re-exported type.
6. Run `make check`.
7. Commit the Go change, `internal/commands/testdata/openapi.json`,
   `ui/src/lib/api-types.generated.ts`, and the UI change together.

When you rebase such a branch and the snapshot or the generated file
conflicts, resolve the conflicts in the code, then run steps 2 and 3 again
instead of merging the generated lines.

Workflow changes span `internal/workflowfile` and `internal/workflowimage`
(the image), `internal/tasks` (the engine, run records, queue secrets, and the
run log route), `internal/workflowrun` (the script protocol, process execution,
and the daemon worker), `internal/taskcli` (`ttasks advance` and the workflow
commands), and `internal/compose` (binding from Compose). Their focused tests
live in those packages. The isolated product path is
`scripts/workflow-e2e.sh` with its fixture under
`scripts/testdata/workflow-e2e/`; it is included by `make full-check` and runs
alone with `make workflow-e2e`. Keep the current behavior documented in
[Task workflows](/docs/task-workflows) and
[Workflow images](/docs/workflow-images).

### Image skill bridge development

Image skill changes span `internal/agentskills`, `internal/imagefile`,
`internal/image`, `internal/imageportable`, `internal/agentdir`,
`internal/harness`, and `internal/loop`. Keep unit fixtures self-contained and
use fake harness executables for deterministic version and capability probes.
The adapter contract version in `internal/harness` is part of the bridge cache
key; bump it whenever generated layout or launch semantics become incompatible.
Keep the pinned Claude Code minimum covered by fixtures, and use
effective-config capability probing for OpenCode instead of guessing a version.
Codex uses no image-skill version probe; cover its escaped, deterministic,
8,000-Unicode-character prompt catalog and both batch/TUI delivery paths.

Every daemon or agent smoke must use isolated `TARIBOY_BASE_DIR` and
`TARIBOY_RUNTIME_DIR` values and an isolated or disabled listener. Focused
real-harness checks are opt-in because they execute locally installed harness
binaries; the Codex check also makes a model request. Cached bridges are
rebuildable agent runtime data and are not
part of runnable image exports or the support-bundle allowlist: exports carry
the canonical image skill tree, and support bundles keep their existing narrow
diagnostic scope.

Run the deterministic fake-harness contract with:

```bash
make smoke-image-skills-contract
```

To add a real-harness check, select one harness or all installed harnesses:

```bash
TARIBOY_IMAGE_SKILLS_REAL_HARNESS=opencode make smoke-image-skills-contract
TARIBOY_IMAGE_SKILLS_REAL_HARNESS=all make smoke-image-skills-contract
```

Claude Code's plugin details and OpenCode's effective config are checked
without a model request. OpenCode also prints a manual `/skills` check. Codex
runs an isolated model-backed iteration, requires it to read the fixture's
absolute `SKILL.md` path, and verifies a proof phrase from the skill body. That
result is reported as model-backed usage, never as native inventory. The smoke
requires `TARIBOY_IMAGE_SKILLS_CODEX_AUTH_JSON` to name an explicit test
credential, copies only that file into the smoke root, and never reads, copies,
or mutates the operator's Codex profile. Set the optional
`TARIBOY_IMAGE_SKILLS_CODEX_CONFIG_TOML` only when that test credential needs a
dedicated config.

### React UI

`frontend-check` and its aggregate entry points install the locked dependencies
before checking. To install them directly while iterating:

```bash
cd ui
npm ci
```

`make check` then covers `npm run fmt:check`, `npm run api-types:check`, `npx tsc -b`, `npm run lint`, `npm run knip`,
`npm test`, `npm run branding:check`, and `npm run bundle:budget`. `make full-check` adds `npm run test:tasks-browser`
and `npm run test:images-browser`, and builds the desktop bundle through its
desktop step. Run any of them directly under `ui/` while iterating:

```bash
cd ui
npm test
npm run api-types
npm run api-types:check
npm run fmt
npm run fmt:check
npm run lint
npm run knip
npm run bundle:budget
npm run complexity:report
npm run build:desktop
npm run test:tasks-browser
npm run test:images-browser
npm run build:store
```

`npm run bundle:budget` runs `ui/scripts/bundle-budget.mjs`. It builds the
production Desktop bundle into a temporary directory, reads the Vite manifest,
and removes the directory afterwards. It checks three sizes against
`LIMITS` in the script:

| Size | Limit in bytes |
| --- | --- |
| The entry chunk | 351,000 |
| The initial JavaScript: the entry chunk and every chunk that it imports statically | 723,000 |
| All JavaScript: every chunk, lazily loaded chunks included | 3,215,000 |

The sizes are minified bytes before compression. Each limit is the size at
the time the limit was set, plus 5%, rounded up to 1,000 bytes. When the code
becomes smaller, lower the limit in the same change. Raise a limit only in the
change that needs it, and give the reason in the pull request.

The failure message names each size that is over its limit, gives the size and
the limit, and lists the files of the initial JavaScript. A missing entry,
manifest import, or output file is also a failure. To fix an entry or initial
failure, load the new code with `React.lazy`, or keep the library out of the
groups that the shell imports (see
[Code splitting](/docs/architecture/web-ui#code-splitting)). To fix a failure
of all JavaScript, make the lazily loaded code smaller.

`npm run fmt` formats `ui/src`, `ui/store`, `ui/tests`, and `ui/.design-sync`
in place with [oxfmt](https://oxc.rs/docs/guide/usage/formatter) and
`ui/.oxfmtrc.json`: double quotes, semicolons, and two-space indentation
without tabs. Import sorting and Tailwind class sorting are off. oxfmt skips
files that it does not support, such as shell scripts, and the paths in
`ui/.gitignore`. `npm run fmt:check`, also available as `make ui-fmt-check`, checks
the same paths without writing files. It is the `ui-fmt-check` step of
`make frontend-check`, so formatting drift fails `make check`. Run
`npm run fmt` when it reports drift. oxfmt 0.73.0 formats some chained calls,
such as `vi.fn().mockImplementation(...)` inside a call, in two passes. If
`npm run fmt:check` still reports a file right after `npm run fmt`, run
`npm run fmt` again. Configure your editor to use oxfmt with
the same configuration, so that a save does not reformat other code.

The commit that first formatted these paths is listed in
`.git-blame-ignore-revs` at the repository root. Use
`git blame --ignore-revs-file .git-blame-ignore-revs FILE` to skip it, or set
it once for your clone:

```bash
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

`npm run lint` runs oxlint with `ui/.oxlintrc.json` and `--deny-warnings`.
A warning therefore fails `make frontend-check` in the same way as an error.
The configuration turns on the complete `correctness` category, adds
selected rules from other categories, and turns on the
[complexity and size thresholds](#frontend-complexity-thresholds). It has
two kinds of rule override: the test override and the `.design-sync` override.
The next section describes them.

Fix the code before you suppress a diagnostic. If a suppression is necessary,
put an oxlint comment on the line before the diagnostic. The comment names the
rule and gives the reason after `--`:

```tsx
// oxlint-disable-next-line react/exhaustive-deps -- keyed by identity on purpose: an equal target keeps the same client
```

A generated file can use one file-level `/* oxlint-disable RULE -- reason */`
comment. Do not use `eslint-disable` comments. `ui/src/test/lintPolicy.test.ts`
fails on an `eslint-disable` comment, on an oxlint comment without a rule or a
reason, and on a rule override of another kind. Turn off a `correctness` rule
for the complete project only when the rule does not apply to the project, and
write the reason in this guide.

#### Frontend complexity thresholds

These are the size and complexity limits for the UI code. `ui/.oxlintrc.json`
turns them on as errors, so `npm run lint`, the `ui-lint` step of
`make frontend-check`, fails on a violation. The diagnostic gives the file, the
line, the function name, the value, and the limit, for example:

```text
src/pages/ExamplePage.tsx:14:16 ... The function `ExamplePage` has too many lines (155). Maximum allowed is 150.
```

| Rule | Limit |
| --- | --- |
| `complexity` | 15 |
| `max-lines` | 400, without blank lines and comments |
| `max-lines-per-function` | 150, without blank lines and comments |
| `max-depth` | 4 |
| `max-params` | 5 |
| `max-nested-callbacks` | 4 |

Test-only files do not have the two length limits. A long `describe` block is
the normal shape of a test file, so a length limit only moves tests around.
The other four limits apply to test-only files in the same way as to app code.
A test with many branches is not reliable: put each case in its own test and
use a route table instead of an `if` chain in a fake server. For a fake
`fetch`, use `routeFetch` from `ui/src/test/fetchRoutes.ts`. The test-only
files are unit tests, Playwright tests, and the shared test code in
`ui/src/test/` and `ui/tests/`:

```json
{
  "files": ["**/*.test.{ts,tsx}", "**/*.pw.ts", "src/test/**", "tests/**"],
  "rules": {
    "max-lines": "off",
    "max-lines-per-function": "off"
  }
}
```

Unlike `make gocyclo`, which does not measure Go test files, these limits
measure the complexity of the frontend tests.

`ui/.design-sync` is the design synchronization tool, not app code. An
override turns off the six limits for `.design-sync/**`. The `correctness`
rules still apply to it.

`make ui-complexity-report` prints every function and file over a limit. When
nothing is over a limit, it prints
`No UI function or file is over a complexity or size threshold.`. It never fails on a violation, like
`make gocyclo-report`. Use it to plan refactoring. Each line gives the rule,
the value and the limit, the file and line, and the oxlint message, which
names the function. The lines are sorted by rule, the largest value first. The
last lines give the number of violations for each rule:

```text
complexity                18/15  src/pages/ExamplePanel.tsx:15   function `ExamplePanel` has a complexity of 18
max-lines-per-function  239/150  src/pages/ExamplePage.tsx:27    The function `ExamplePage` has too many lines (239)

complexity: 1
max-lines-per-function: 1
total: 2
```

If a test file becomes slow, divide it into one file for each scenario, for
example `TasksWorkspace.realtime.test.tsx`. Vitest runs the files in parallel.
Put the shared fixtures in `ui/src/test/`. Keep the `vi.hoisted` and `vi.mock`
calls in each test file, because Vitest hoists them only in the test file
itself.

`npm run knip` runs [Knip](https://knip.dev) from `ui/knip.json`. The
`ui-dead-code` step of `make frontend-check` runs it. It fails when it finds
unused code or an unused package, and it does not delete code. It runs two
passes:

1. `knip --production --include files` follows imports from the Desktop and
   Android app (`src/main.tsx`, found through `index.html`) and from the Store
   app (`store/main.tsx`, found through `vite.store.config.ts`). Tests,
   `tests/**`, and `.design-sync/**` are not entry points in this pass. A file
   that only a test or the design-sync bundle imports is reported as unused.
2. `knip` checks the complete graph: the apps, the Vitest unit tests, the
   Playwright tests and fixtures under `tests/`, and the design-sync files
   under `.design-sync/`. It reports every issue type: unused files, exports,
   exported types, duplicate exports, unused or unlisted dependencies and
   devDependencies, and unlisted binaries. An export that a test imports is
   not reported, but an export that no file imports is.

Knip finds entry points in three ways. Its Vite, Vitest, and Playwright
plugins read every `vite*.config.ts` and `playwright.*.config.ts` file in
`ui/`, so a new config with a name of that form needs no change. The `entry`
list in `ui/knip.json` adds `tests/**` and `.design-sync/**`, because a
script or an external tool loads those files by path, not by import. A new
file that is loaded by path, by a glob, or by a tool outside the import graph
must be added to `entry`. Otherwise Knip reports it as an unused file. The
`project` list names the files that can be reported. It includes `*.css`
under `src/` and `store/`, so a package used only by a CSS `@import`, such as
`tailwindcss`, counts as used.

The report has one group for each issue type, for example
`Unused files (1)` or `Unused exported types (2)`. Each line gives the name,
the file, and the line. Fix each group as follows:

| Group | Fix |
| --- | --- |
| Unused files | Delete the file. If a tool loads it by path, add it to `entry` |
| Unused exports, exported types | Delete the code, or remove the `export` keyword when only its own file uses it |
| Duplicate exports | Keep one name and delete the alias |
| Unused dependencies, devDependencies | Remove the package with `npm uninstall` |
| Unlisted dependencies | Add the package to `package.json` with `npm install` |
| Unlisted binaries | Add the npm package that provides it. A tool that is not an npm package, such as `go`, goes to `ignoreBinaries` |

If Knip reports unlisted binaries such as `oxfmt` or `knip` that are in
`package.json`, `ui/node_modules` is out of date: run `npm ci` in `ui/`.
Shared test helpers live under `src/test/`,
which the first pass does not check. Add an exception to `ignoreIssues` in
`ui/knip.json` only for code that the app does not use on purpose. Name each
file, list only the issue types it needs, and give the reason in the pull
request. Do not add a pattern that covers all of `src/` or all components.
The current exceptions are the shadcn primitives under `src/components/ui/`.
The repository keeps that kit complete for the design-sync catalog, so its
unused exports and the unused `separator.tsx` and `tooltip.tsx` files are
allowed.

The design-sync catalog under `ui/.design-sync` is checked by `make check` in
two places. `npx tsc -b` builds `ui/tsconfig.design-sync.json`, which
type-checks `.design-sync/entry.tsx` and every preview against the real
component props: the `tariboy-ui` import in a preview resolves to the
generated entry. When a component's props change, update its preview in the
same change. `src/test/designSyncCatalog.test.ts` fails when the committed
`entry.tsx` differs from a fresh `node .design-sync/make-entry.mjs` run, when a

or an override has no `componentSrcMap` key. To fix the first case, run
`node .design-sync/make-entry.mjs` from `ui/` and commit the result. For the
other cases, correct `config.json`.

### Rust desktop host

Neither entry point runs the Rust tests or clippy — `full-check` compiles this
crate through its desktop step, but does not test it. Run them yourself when
changing `desktop/src-tauri`:

```bash
. "$HOME/.cargo/env"
cd desktop/src-tauri
cargo test
cargo clippy --all-targets -- -D warnings
```

On Linux, install the native Tauri prerequisites plus user-local toolchains:

```bash
# Go 1.26 must precede an older distribution Go in PATH.
export PATH="$HOME/.local/toolchains/go1.26.5/bin:$PATH"

. "$HOME/.cargo/env"
rustup default stable
cargo install tauri-cli --version "^2" --locked
cargo install tauri-driver --locked
```

The OS must provide `libwebkit2gtk-4.1-dev`, `WebKitWebDriver` (Ubuntu package
`webkit2gtk-driver`), and a usable display. Headless machines also need Xvfb
(Ubuntu packages `xvfb` and `x11-xkb-utils`). Override discovery with
`TAURI_DRIVER_BIN`, `WEBKIT_WEBDRIVER_BIN`, or `TARIBOY_XVFB_BIN` when those
executables are installed in user-local paths; include their library directory
in `LD_LIBRARY_PATH` when they were extracted from packages rather than
installed system-wide.

`make desktop-e2e-build` checks all three up front through
`make desktop-e2e-tools-check`, so a missing one fails once — naming the tool,
how to install it and which variable overrides it — before the Go, SPA and
Tauri builds start, instead of repeating itself once per spec after them. The
check honours the same override variables as the fixture, and only demands
Xvfb when `DISPLAY` is empty. `make desktop PLATFORM=linux` does not depend on
the WebDriver toolchain.

Build the production SPA and bundled payloads into a WebDriver-ready,
non-packaged Linux debug executable, then run every real Desktop E2E spec:

```bash
make desktop-e2e-build
make desktop-e2e
```

The Desktop suite runs independent specs in two workers by default. Each worker
still starts a real Tauri/WebKit stack and receives separate owner-only daemon,
runtime, app-data, display, and driver-port state. Set
`DESKTOP_E2E_WORKERS=1` for a constrained host; do not raise the default without
measuring the resulting WebKit and daemon resource use.

The executable is
`desktop/src-tauri/target/debug/tariboy-desktop`. No `.deb` or `.AppImage`
is produced. Run one spec while iterating with:

```bash
make desktop-e2e DESKTOP_E2E_ARGS="tests/desktop/cold-start.pw.ts"
```

Specs live under `ui/tests/desktop/` and import the shared fixture from
`fixture.ts`. Playwright owns suite organization, assertions, timeouts, and
failure artifacts; its small typed W3C client sends commands through
`tauri-driver` to the real Tauri WebKit WebView. Add future product scenarios as
new `*.pw.ts` specs and reuse the fixture instead of launching another driver
inside a test.

Each fixture run creates fresh owner-only base, runtime, and Desktop app-data
directories, rejects the live `127.0.0.1:9990` listener, chooses free driver
ports, and stops its isolated daemon before removing temporary state. It never
stops or reconnects the user's live daemon. If `DISPLAY` is unset, the fixture
starts its own Xvfb and terminates it during cleanup. Failed setup includes
bounded Xvfb, driver, and daemon diagnostics in the Playwright report.

From the repository root, `make desktop` builds the Desktop UI, both platform
binary payloads, and native packages for the selected platform. `PLATFORM`
defaults to the supported native host and accepts `darwin` or `linux`; it does
not enable cross-compilation. A standalone invocation runs `npm ci` when
`ui/node_modules` is absent, using the committed lockfile before it builds the
SPA. Verification entry points already install Node packages, so their Desktop
step skips that duplicate work.

On Darwin arm64:

```bash
make desktop PLATFORM=darwin  # .app and .dmg
make desktop-smoke
make desktop-mac
```

The Darwin recipe sets `CI=true` only for `cargo tauri build`. This
selects Tauri's supported headless-safe DMG path: the disk image and
`Applications` link are still created, but Finder AppleScript is skipped.
Packaging therefore does not depend on an interactive macOS Automation grant.

On Linux x86_64:

```bash
make desktop PLATFORM=linux  # .deb and .AppImage
```

The preflight rejects unknown platform values, unsupported host architectures,
and a platform that does not match the current host before compiling payloads.

Ordinary `make desktop` packages keep Tauri updater artifacts disabled, so local
macOS and Linux builds do not need the release owner's private key. The macOS
path still creates the ad-hoc-signed app and DMG.

`make desktop-mac` is the signed release path. It requires
`TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, enables the
Tauri updater archive and signature explicitly, and fails before packaging when
either variable is missing. The release owner permanently owns and backs up that
private key; its matching public key is pinned in the Desktop bundle. Never print
or commit the signing Secrets. Key rotation requires a separately planned
release because installed applications trust the embedded public key.

Tauri runs the macOS disk image through its own `bundle_dmg.sh` and reports a
failure there as a bare `failed to run bundle_dmg.sh`, without that script's
output. When bundling fails, `make desktop-mac` therefore prints
`scripts/desktop-bundle-diagnostics.sh` — host, free disk space, attached disk
images, mounted volumes, running disk image processes, and the partial bundle
output — and then reproduces the failure once with `DESKTOP_BUNDLE_VERBOSE=1`,
which passes `--verbose` to `cargo tauri build` so the bundler streams
`bundle_dmg.sh`'s own error. A build that fails twice ends with both reports in
the log; a build that succeeds only on that retry says so instead of passing
silently. The reporter never fails and names any tool it cannot run, so it can
be called on its own:

```bash
scripts/desktop-bundle-diagnostics.sh
```

Pushing an exact `vX.Y.Z` tag whose version matches both canonical declarations
runs the same target on GitHub's `macos-15` runner. The workflow requires both
signing Secrets, finds the single generated `.app.tar.gz` and `.sig` pair, and
stages them with the checked DMG, `SHA256SUMS`, `release.json`, and `latest.json`.
Before staging, the manifest gate rejects malformed packets or a signature key
identifier that differs from the public key in `tauri.conf.json`. This identifies
an accidental wrong signing Secret; cryptographic archive verification remains
the installed updater's responsibility. A separate `publish` job waits for this
macOS job and the Android job (see [Android app](#android-app)), creates a draft
GitHub Release, uploads the complete set together with the signed APK, and only
then makes the release public, so the latest catalog cannot reference missing
assets and a failed Android build publishes nothing. The first updater-enabled version
must still be installed from the DMG; only later, higher signed versions can be
installed by the updater.

A tag run can restore only caches saved by its own tag or by `main`, so the
release job restores the Cargo cache but never saves one.
`.github/workflows/desktop-cache.yml` saves it instead: on `main`, it builds the
Desktop Rust dependencies with the cargo command `cargo tauri build` uses, under
the shared `desktop-release` cache key. It runs when `desktop/src-tauri/Cargo.lock`
or `Cargo.toml` changes on `main`, weekly, and on manual dispatch. If the cache
is missing or evicted, the release still succeeds and compiles every
dependency.

The tray action **Install/Update CLI** owns the local five-file payload and
six-command-path install. It preflights and atomically switches `tariboyd`,
`tariboy`, `tariboy-tasks`, `ttasks`, `tariboy-shim`, and
`tariboy-plugin-telegram` links under `~/.local/bin`; `ttasks` points to the
real `tariboy-tasks` payload. It then restarts the bundled daemon even when the
links already target the same app path. Its filesystem and lifecycle work must
stay off the UI thread. Changes to
this flow require Rust installer tests plus the daemon restart-handoff tests;
never exercise it against the user's live daemon.

### Android app

The Android app is the same SPA in a Tauri WebView, built in Android mode
(`npm run build:android`, `VITE_TARIBOY_SHELL=android`). Its Rust side is the
mobile entry point in `desktop/src-tauri/src/lib.rs`: no commands, daemon, SSH,
tunnels, or bundled Go binaries. Its only plugins are a navigation guard and
`tauri-plugin-opener` (a mobile-only dependency, pinned to the release line
that matches the locked `tauri`), which keep web links out of the WebView.
The navigation callback cancels an external web link without waiting for the
browser. It copies the URL and app handle into a `spawn_blocking` task that
calls the opener. The Android opener waits for a response from the UI thread,
so calling it inside the navigation callback can deadlock that thread.
If opening fails, the current page stays in place. The host logs a fixed
message without the URL or error details and shows no message in the UI.
The guard's decision, `navigation_for`, is a plain function with unit tests that
`cargo test` runs on the host; `cargo check --lib --target aarch64-linux-android`
compiles the entry point without the Android SDK. Host Rust tests also cover
the callback returning while an opener waits, unchanged URL delivery, blocked
and internal navigation, and failed browser attempts. `make check` does not
run these Rust tests or test browser opening on an Android device.
`tauri.android.conf.json` swaps
in that SPA build and drops the bundled resources. The Gradle project under
`desktop/src-tauri/gen/android` is generated by `cargo tauri android init` and
committed; it adds `res/xml/network_security_config.xml` (plain http only to
`127.0.0.1`, `localhost`, and `::1`), Android launcher icons generated from
`desktop/branding`, release signing from an ignored `keystore.properties`, and
a `MainActivity` that pads the edge-to-edge WebView by the system bars, the
display cutout, and the keyboard. Keep that padding after a regeneration;
`scripts/android_activity_test.go` checks it.

Building needs a JDK 17 or newer, the Android SDK with a platform and
build-tools in `ANDROID_HOME`, and an NDK in `NDK_HOME`:

```bash
export ANDROID_HOME=$HOME/Android/Sdk
export NDK_HOME=$ANDROID_HOME/ndk/27.2.12479018
make desktop-android
```

The target builds an `arm64-v8a` release APK under
`desktop/src-tauri/gen/android/app/build/outputs/apk/universal/release/`. With
`desktop/src-tauri/gen/android/keystore.properties` (`storeFile`,
`storePassword`, `keyAlias`, `keyPassword`) the APK is signed; without it the
output is `*-unsigned.apk` for local checks.

The release workflow builds it in a parallel `android` job on `ubuntu-latest`
and requires four repository Secrets, `ANDROID_KEYSTORE_BASE64` (the
base64-encoded keystore), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, and
`ANDROID_KEY_PASSWORD`, plus the repository variable `ANDROID_CERT_SHA256`. The
job rejects an unsigned APK, a debug certificate, and any certificate whose
SHA-256 fingerprint differs from that variable, and `publish` writes the
fingerprint into the release notes. [Android release APK](/android-release)
describes the key, the GitHub settings, and the failure messages.

## Test isolation

Any test daemon or agent must use its own data directory, runtime directory,
and listener configuration. Never stop, restart, reuse, or point test tooling at
the user's live daemon, `~/.tariboy`, `~/.tariboyd`, or
`127.0.0.1:9990`.

For an ad-hoc daemon:

```bash
test_base="$(mktemp -d)"
test_runtime="$(mktemp -d)"
TARIBOY_BASE_DIR="$test_base" \
TARIBOY_RUNTIME_DIR="$test_runtime" \
./bin/tariboyd --http-addr ""
```

Remove the temporary directories only after the isolated process is confirmed
stopped. The repository smoke and end-to-end scripts already enforce their own
isolation.

:::danger
A second daemon using the live base directory shares the SQLite database and
loop managers. It can double-execute iterations, reconcile the same agents, and
reap live sessions. Isolation is a data-safety requirement.
:::

### Go test isolation and speed

Go tests follow these rules so the suite stays fast, parallel, and away from
live state:

- **Test databases come from `internal/store/storetest`.** `storetest.Open(t)`
  returns a migrated database in a temporary directory, and
  `storetest.OpenAt(t, path)` does the same at a given path.
  `storetest.Seed(t, path)` writes a migrated file for code that opens the
  database itself, such as `daemon.Run`. The first call in a test binary
  runs the real migrations once; every later call copies that template. Call
  `store.Open` directly only to reopen an existing file or to test migrations.
- **Packages whose tests start a daemon, a loop manager, or the CLI call
  `testutil.IsolateEnv()` from `TestMain`.** It removes every `TARIBOY_`
  variable and points `HOME` at a temporary directory. The suite passes with
  `TARIBOY_RUNTIME_DIR` and `TARIBOY_BASE_DIR` set to paths that do not
  exist. `loop.NewManager` never reads the environment: tests pass
  `RuntimeDir` (use `testutil.ShortDir(t)` for socket paths) and may pass
  `BaseEnv`.
  For nested `go build` commands only, pass `testutil.RealHome()` as the child
  process's `HOME` to reuse Go caches. Keep the test process and built binaries
  on their isolated `HOME`.
- **Wait for state, not for time.** Use `testutil.WaitFor` instead of a
  `time.Sleep` loop, and prove that something did not happen with a hook, a
  fake timer, or `testing/synctest`. A `time.Sleep` that must stay in a test
  has a comment that says why. A test that starts `daemon.Run` waits on
  `Options.Ready` instead of polling the daemon socket.
- **Mark independent tests with `t.Parallel()`.** Tests that use `t.Setenv`,
  `os.Chdir`, or package-level state stay sequential.
- **Tests that drive a real `tmux` have the `tmux` build tag**
  (`internal/shim/shim_tmux_test.go`). `make test` adds `-tags tmux` when
  `tmux` is installed, and `make vet` always vets them. Run them alone with
  `go test -tags tmux ./internal/shim/`.

## Change workflow

1. **Understand:** read the task, this guide, and topical docs; inspect current
   code, tests, and recent changes.
2. **Design or diagnose:** agree on behavior before feature work; establish root
   cause before bug fixes.
3. **Protect behavior:** add a focused failing test for code changes, or define
   an executable validation for documentation and scripts.
4. **Implement narrowly:** preserve unrelated work and avoid opportunistic
   refactors.
5. **Synchronize docs:** update operator, architecture, reference, and
   contributor docs whenever behavior, commands, prerequisites, or boundaries
   change.
6. **Verify:** run every relevant row from the verification matrix plus
   `git diff --check`.
7. **Review:** inspect the complete diff for correctness, security, generated
   files, and scope before committing.
8. **Commit:** use a focused message and report what was verified.

## Versioning

Ordinary tasks, including code-changing tasks, do not bump the version. Move
the canonical version only when cutting a release, by running
`scripts/set-version.sh NEW_VERSION`, the single supported mechanism.
Hand-editing a pinned version file is not supported. This release-time policy
prevents version-pin merge conflicts that previously forced implementation
chains to run one at a time.

Choose the release version from everything landed since the previous release:

- use a patch bump for bug fixes, refactoring, performance work, test-only code
  changes, build tooling, and other changes that add no user-facing capability;
- use a minor bump for new commands, APIs, UI capabilities, or other
  user-facing functionality;
- while the product remains on `0.x`, also use a minor bump for an intentional
  incompatible behavior change unless the user specifies another release
  decision;
- use the highest-impact category when a release includes several changes.

`internal/version.Version` is the canonical full version.
`scripts/set-version.sh` writes `scripts/release-version.txt`, a second
declaration of that value, at the same time and no other mechanism writes it.
A disagreement proves the supported mechanism was bypassed and fails the
release gate. After `make build`, verify that `./bin/tariboy version` and
`./bin/tariboy --version` print the exact canonical value; do not use
`make install` merely to put a build on `PATH`.

## Definition of done

A change is complete when:

- the requested behavior and scope are implemented;
- focused regression tests and the affected subsystem suites pass;
- formatting, lint, vet, or Clippy passes for each changed language;
- daemon and agent tests used isolated state;
- generated artifacts match their documented Git contract;
- current documentation describes the resulting behavior and commands;
- release cuts use exactly one appropriate patch or minor version bump through
  `scripts/set-version.sh`;
- every new documentation link resolves and the docs site builds;
- `git diff --check` passes;
- the final diff contains no unrelated edits, credentials, or temporary files;
- Important and Critical review findings are resolved.
