# Channels and Agent Message Delivery

This document describes the v2 channel bus: how messages move through channels,
how agents receive them, how deliveries are acknowledged, and which agent
settings affect message handling.

## Mental model

The bus is a store-backed fan-out system with four core tables:

- `channels`: named streams such as `agent:worker:inbox` or `group:dev-team:broadcast`.
- `messages`: immutable message rows published to a channel.
- `subscriptions`: an agent's standing interest in a channel, optionally filtered.
- `deliveries`: one per matching `(subscription, message)` pair; this is the per-agent queue.

Publishing to a channel does not push text directly into an agent process.
Instead, `Publish` writes the message and creates delivery rows for all matching
subscriptions. An agent receives messages only when its loop starts an iteration
and the runner drains pending deliveries into that iteration's prompt.

## Channel names and kinds

Valid operator-managed channel names use a known prefix and `:`-separated
segments. Each segment must match `^[a-z0-9][a-z0-9_-]*$`.

Known prefixes:

- `agent`
- `group`
- `user`
- `chat`

Built-in helpers define the main system channel shapes:

- `agent:<agent>:inbox`: direct inbox for one agent.
- `agent:<agent>:stream`: stream channel for one agent.
- `group:<group>:broadcast`: fan-out channel for all members of a group.
- `group:<group>:inbox`: group lead inbox.
- `group:<group>:direct:<agent>`: direct group lane; currently helper-defined, not the main group workflow.
- `chat:<name>`: chat/plugin-facing channel.
- `chat:telegram:<agent>`: the bundled Telegram topic for one agent.
- `user:<name>`: user-facing channel.

Channel kind is inferred from the name:

- `agent_inbox`
- `agent_stream`
- `group_inbox`
- `group_broadcast`
- `group_direct`
- `user`
- `chat`

Unknown shapes default to `chat` kind in low-level classification, but operator
subscription validates channel names before creating them.

The Telegram plugin subscribes the mapped agent and its sink to the concrete
`chat:telegram:<agent>` channel. Authorized topic text is published as a normal
plugin-produced message; an agent-produced reply is delivered back to that
topic only after it passes through the same durable bus. The plugin suppresses
its inbound echo and acknowledges the sink delivery only after Telegram accepts
the reply.

## Messages

A message has:

- `id`: generated by the bus from channel + timestamp + sequence.
- `channel`: target channel.
- `ts`: fixed-width timestamp used for chronological ordering.
- `source`: producer identity such as `operator`, `agent:<name>`, or plugin source.
- `type`: free-form type string used by filters.
- `subject`: structured JSON object, usually shallow metadata.
- `text`: human-readable text body.
- `data`: structured JSON object.
- `produced_by_agent`, `produced_in_iteration`, `produced_by_plugin`: attribution fields.

Operator publish:

```bash
tariboy message send --channel chat:ops --type note --text "hello"
```

Agent publish from inside an iteration:

```bash
tools message send --channel chat:ops --type note --text "hello"
```

Group request is a convenience wrapper over normal message publish:

```bash
tools group request worker --text "What is blocking you?" --deadline 5m
```

It publishes to `agent:worker:inbox` with type `group.request` and
`data.deadline = "5m"` after checking that `worker` is in the caller's group.

## Subscriptions

A subscription belongs to one agent and one channel. It can also include:

- `matcher`: content matcher over `source`, `type`, `subject.*`, and `data.*`.
- `type_filter`: list of type globs.

An empty matcher and empty type filter match all messages on the channel.
Subscriptions are idempotent on `(agent, channel, matcher)`.

Agent-side subscription tools:

```bash
tools channel subscribe chat:ops
tools channel subscribe chat:ops --type incident.*
tools channel subscribe chat:ops --matcher '{"subject.env":"prod"}'
tools channel ls
tools channel unsubscribe <subscription-id>
tools sources
```

Operator-side subscription commands:

```bash
tariboy agent subscribe worker chat:ops
tariboy agent unsubscribe worker chat:ops
tariboy agent subscriptions worker
```

The operator path lists subscriptions by distinct channel, not by raw
subscription id. Protected subscriptions cannot be removed through the operator
unsubscribe command:

- the agent's own `agent:<agent>:inbox`;
- any `group:*` channel.

These are managed by the system/group provisioner. Every persisted agent owns
the unfiltered subscription to its own inbox: creation provisions it and daemon
startup repairs missing legacy subscriptions before loop engines start.

## Publish, fan-out, and per-agent queues

`Publish` is atomic:

1. Ensure the channel row exists.
2. Insert the message.
3. Load subscriptions for that channel.
4. For each subscription whose `type_filter` and `matcher` match, insert a
   delivery row.
5. Commit the transaction.
6. Call the publish hook with the set of agents that received at least one
   delivery.

The queue is therefore not a separate queue table per agent. It is the set of
unacked, non-DLQ delivery rows for subscriptions owned by that agent.

The daemon wires the publish hook to wake affected agent loops. A wake is only a
nudge: the engine checks `HasPending(agent)` and starts a message-triggered
iteration only when the agent's loop is enabled and pending deliveries exist.
Native Task assignment and mention notifications use this same path; they do
not call a Tasks-specific runner or poller. A disabled loop keeps the delivery
pending until it is enabled or started manually.

### Idle task reminders

`task_reminder` is a daemon configuration policy for an idle agent with
assigned Native Tasks. With no saved value it is off and uses
`idle_threshold_s: 300`; the threshold is a positive integral number of
seconds. Its eligibility is independent of timer cadence, so an agent with
`interval_s=0` can qualify. The policy must be enabled, as must the agent and
its loop; the agent must have assigned open Native Tasks and have passed the
idle threshold since its latest durable activity boundary.

For each eligible generation, the reconciler publishes one normal
`task.reminder` message to `agent:<name>:inbox`. Its saved fingerprint combines
the sorted assigned-open task keys with the activity boundary, deduping repeated
scans and daemon restarts. A changed assignment set or a newer completed
iteration makes a new generation eligible after the threshold. The order is
strictly `Publish -> delivery -> WakeMessage`: no direct iteration starts, and
disabled loops retain a pending delivery. The message is only a reminder; it
does not claim, assign, or change a Native Task.

### Workflow-owned channel use

A managed assignment is deliberately different from an agent's standing bus
subscriptions. Direct message publishing, group coordination, and raw channel
management are denied by default for its active iteration. The workflow packet
may expose explicit direct tools, while task-related observation subscriptions
are created with `tasks observe subscribe` and must match a workflow-declared
channel pattern.

A matching message is appended as an observation. It never supplies a free-form
state transition: only `record_only`, `wake_current`, `hold_assignment`, or
`create_requirement` may run, and only when declared by the pinned workflow.
Late messages are retained as record-only evidence. Operator queue triggers are
separate: an external plugin event may create a new task, after which ordinary
queue workflow pinning applies. See [Configurable task workflows](/docs/task-workflows).

## Pending delivery and prompt injection

At iteration prepare time, the runner drains a batch:

```go
msgs, err := Bus.Pending(agentName, messagesBatch)
```

`Pending` returns messages ordered by `(ts, id)` oldest-first. If several
subscriptions for the same agent match the same message, the message is deduped
in the prompt, while all returned delivery rows are accounted.

Calling `Pending` also marks returned delivery rows as delivered:

- sets `delivered_at`;
- increments `attempts`;
- if the next attempt would exceed `maxAttempts`, marks the delivery `dlq=1`.

The max attempts constant is currently `5`.

The messages are written into the prompt under:

```text
# Messages
Incoming messages for this iteration (newest last):
...
```

Despite the section text saying "newest last", the practical result is
chronological order: older messages appear first, newer messages later.

## Ack and redelivery

The runner remembers the message ids it put in the prompt. After the harness
finishes, it acknowledges those ids only when:

- the runner itself did not error;
- at least one message id was batched;
- the iteration outcome is `done` or `no_i_am_done`.

Ack sets `acked_at` on delivery rows for that agent and those message ids.

Important implication: ack means "the message was included in an iteration that
finished normally enough", not "the agent semantically handled the message".
`no_i_am_done` still acks. Harness errors, timeouts, killed iterations, and
runner errors do not ack, so messages can be redelivered until they hit DLQ.

## Groups

Groups provision channels and subscriptions automatically.

For a group named `dev-team`:

- all members subscribe to `group:dev-team:broadcast`;
- each member subscribes to its own `agent:<member>:inbox`;
- the lead subscribes to `group:dev-team:inbox`;
- non-lead members are not subscribed to the group inbox.

`tools group request <member> ...` and `tools group send <member> ...` publish
directly to the member's `agent:<member>:inbox`, not to the group broadcast.

`group:<group>:inbox` is the external entry point for the lead. Broadcast is the
lead/member fan-out channel.

## Schedules and scripts

Schedules are agent-owned bus producers. A schedule has:

- `agent`
- `kind`: `oneshot` or `cron`
- `spec`
- `channel`
- `message_template`
- `next_fire_at`
- `enabled`

Agent tools can create schedules:

```bash
tools schedule add --kind oneshot --spec 2026-07-10T10:00:00Z
tools schedule add --kind cron --spec "*/15 * * * *" --channel agent:worker:inbox --message '{"text":"wake"}'
tools schedule ls
tools schedule cancel <id>
```

If no channel is passed, the agent API defaults the schedule target to the
agent's own inbox.

Scripts are also agent-owned, but they execute only local commands; they do not
schedule arbitrary channel publication. `tools script run NAME -- COMMAND`
queues one attempt, while `tools script schedule NAME --every N -- COMMAND`
runs immediately and then after a fixed post-completion delay. Non-quiet runs
publish `script.result` to the owner's inbox. Its structured data contains
script/run IDs, name, mode, status, optional exit code, and absolute `log_path`.
Combined stdout and stderr remain in that file and are not copied into the
message.

## Operator visibility

Useful operator commands:

```bash
tariboy channel ls
tariboy channel inspect <channel>
tariboy channel tail <channel>
tariboy channel tail <channel> -f
tariboy message send --channel <channel> --text "..."
tariboy agent subscriptions <agent>
tariboy agent subscribe <agent> <channel>
tariboy agent unsubscribe <agent> <channel>
```

`channel tail` reads messages on a channel. It does not show per-agent delivery
state such as `acked_at`, `attempts`, or DLQ.

## Agent configuration that affects channels

The agent row contains these message-related fields:

- `messages_batch`: maximum number of pending messages inserted into one prompt.
  Default is `10`. If the runtime value is `<= 0`, the runner also falls back to
  `10`.
- `messages_max_queue`: maximum pending messages for the agent, default `1000`.
  A publish beyond the limit is retained in that agent's DLQ with result
  `queue_limit`; it is not added to the runnable pending queue.
- `loop_enabled`: if false, publish can create pending deliveries but the agent
  will not run automatically to consume them.
- `interval_s`: timer-based loop interval. Message-triggered iterations do not
  require a positive interval; they require loop enabled and pending messages.
- `group`: group membership. This controls automatic group/broadcast/inbox
  subscriptions and shared group behavior.
- `plugins`: every agent has core `messages` capability through plugin
  resolution; optional plugins such as `schedule` and `scripts` expose extra
  agent-side tools.

Creation-time options that matter:

```bash
tariboy agent run image:tag --name worker --group dev-team --loop=true
```

Loop/runtime controls:

```bash
tariboy agent start worker
tariboy agent stop worker
tariboy loop interval worker <seconds>
```

Inside an agent:

```bash
tools loop start
tools loop stop
tools channel subscribe <channel>
tools channel unsubscribe <subscription-id>
```

There is currently no public CLI command dedicated to changing
`messages_batch` or `messages_max_queue` after creation.

## Common workflows

Direct worker request from a lead:

```bash
tools group request worker --text "Please take TARI-12" --deadline 5m
tools group loop start worker
```

Broadcast to a group:

```bash
tools message send --channel group:dev-team:broadcast --type note --text "Stand by"
```

Subscribe an agent to a plugin/chat channel:

```bash
tariboy agent subscribe worker chat:messenger:ops
```

Inspect whether messages are being published:

```bash
tariboy channel tail chat:messenger:ops -f
```

Inspect whether an agent is subscribed:

```bash
tariboy agent subscriptions worker
```

## Failure modes and debugging

- Message published, agent does not see it:
  - Check the agent is subscribed to the channel.
  - Check the agent loop is enabled.
  - Check the message type and matcher filters.
  - Check whether previous delivery attempts hit DLQ.

- Message appears repeatedly:
  - The previous iteration likely did not ack it because the runner errored,
    timed out, or was killed.

- Group request not received:
  - Confirm both caller and target are in the same group.
  - Confirm target has its `agent:<target>:inbox` subscription.
  - Start the target loop if it is disabled.

- Operator cannot unsubscribe a channel:
  - It may be protected (`agent:<agent>:inbox` or any `group:*` channel).
