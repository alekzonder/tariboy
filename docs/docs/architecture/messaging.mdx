Every message in Tariboy is a **letter** from one principal to another, stored
in one SQLite table, `mail` (service in `internal/mail`, schema in
`internal/store/migrations/0072_mail.sql`). An agent has an inbox; a letter in
it wakes the agent's loop; the agent answers it. This page is the architectural
summary; the [mail reference](/docs/reference/mail) covers `tmail`,
`tariboy mail`, the routes and debugging.

## One table, three views

A letter has a sender, a recipient, a subject, a body, a `kind` (`message`
unless the producer names another, such as `task.question` or
`script.result`), a JSON `data` object and its state. A send to several
recipients writes **one row per recipient**, each with its own id and state, so
a broadcast shows one row per recipient in the sender's Sent view.

Every mailbox is a filter over that table:

| View | Rows of principal P |
| --- | --- |
| Inbox | `recipient = P`, still open (`answered_at` and `dead_at` empty), oldest first |
| Sent | `sender = P`, newest first |
| Archive | `recipient = P`, closed or dead, newest first; dead letters are tagged |

So an operator reads exactly what an agent saw, sent and answered, and nothing
is stored beside the table "for the transport": per-recipient state lives on
the letter row. Answering never deletes a letter.

## Principals

| Principal | Who | As a recipient |
| --- | --- | --- |
| `agent:<name>` | an agent | must exist; its inbox wakes its loop |
| `user:<login>` | the customer | must be the customer login; read in the Desktop or with `tariboy mail` |
| `plugin:<name>` | a plugin | must be installed; the plugin host delivers the letter to the plugin's `/deliver` |
| `system:<component>` | a daemon component | always accepted; stored closed, because nothing reads a system inbox |
| `queue:<prefix>` | a task queue | must exist; stored closed; exists for [queue triggers](#queue-triggers) |
| `group:<name>` | an alias | expands to every group member except the sender |

Any other recipient is refused with `unknown_recipient`, and a group whose only
member is the sender with `empty_group`. A sender must be an existing agent,
the customer, an installed plugin or a `system:*` component.

The customer login is a fixed value rather than the account `tariboyd` runs
as, so `user:customer` names the same person on every server. It defaults to
`customer` and is overridable through the `customer_login` key in
`daemon_config`. On the first start without a stored `customer_login`, the
daemon writes `customer` and moves earlier customer principals, in tasks,
comments, waits and letters, to `user:customer` in one transaction. Changing
the key later rewrites nothing.

## Requests and notices

Every letter is a **request** or a **notice**, chosen by its sender:

- A request needs an answer. It leaves the inbox when its recipient replies.
- A notice needs no answer. It leaves the inbox when its recipient has read it.

A reply goes to the original sender with subject `Re: <subject>` and
`in_reply_to` set, and closes the original in the same transaction. A reply is
a notice unless the sender marks it as a request (`tmail reply --ask`).
Without this split every answer would be a new obligation: two agents would
answer each other until the attempt limit, and every answer to the customer
would wait in the customer's inbox.

A reply to a closed letter is recorded and reopens nothing. A reply to a
`task.question` letter is refused with `answer_on_task`: the answer belongs on
the task, and the tasks service closes the letter.

## When a letter closes

Closing sets `answered_at`. A reply also sets `answer_id`; any other close
leaves it empty and records a `close_note`.

| Recipient | A request closes when | A notice closes when |
| --- | --- | --- |
| `agent:*` | the agent replies | it was rendered into an iteration that finished successfully (`close_note = read`) |
| `user:*` | the customer replies or archives it | the customer opens it in the Desktop or runs `tariboy mail read` (`read`) |
| `plugin:*` | the plugin's `/deliver` accepts it (`delivered`) | the same |
| `system:*`, `queue:*` | at once: stored closed | at once |
| any, `task.question` | the question is answered on the task (`task-comment:<id>`), or a workflow outcome resolves it (`task-outcome:<status>`) | — |

An operator can archive any letter without a reply (`tariboy mail close`,
with an optional note). The agent tool has no archive: an agent answers.

A notice rendered into an iteration that ends in an error, a timeout or a kill
stays open and is rendered again next iteration, like a request.

## Attempts and dead letters

- Rendering a letter into a prompt adds one to its `attempts` in the same
  transaction that reads it. A letter whose next render would be its sixth is
  marked dead with reason `attempts` instead of being rendered.
- A letter to an agent whose open inbox already holds `messages_max_queue`
  letters (default 100) is stored dead with reason `queue_limit` and wakes
  nothing. So the limit bounds runnable work, not mail storage.
- A row whose `data` does not decode is marked dead with reason
  `decode_error`; the other letters are still rendered.
- A dead letter sits in the recipient's Archive. **Requeue** clears its dead
  state, attempts and close fields and puts it back in the inbox.
- A send with an idempotency key that the recipient already holds returns the
  existing letter and writes nothing. Native Tasks' notification outbox,
  schedules, the Goal reconciler, script results and plugins use it.
- **Clear** deletes every open letter of one agent (`tariboy mail clear --as
  agent:NAME` or `POST /api/agents/{name}/mail/clear`); closed and dead
  letters stay.

Maintenance purges closed letters older than the more recent of the retention
period and `chat_retention_days` (the field kept its name), and never a letter
to a queue that the workflow ingress has not consumed yet.

## Wake path

```text
Send ─▶ one row per recipient (one transaction)
     └▶ after commit: wake hook ─▶ Manager.WakeAgents(agent recipients)
                      event hook ─▶ one /api/mail/ws hint per row
                      plugin wake ─▶ drain plugin:<name> inboxes
```

The loop starts a message-triggered iteration only for a started agent whose
open inbox count is above zero; a positive `interval_s` is not needed. A
stopped agent keeps its letters open until it is started. At prepare time the
runner reads the oldest open letters, requests first and notices after them,
up to `messages_batch` (default 10), and renders them into the `## Messages`
section of the prompt with the standing instruction that names
`tmail reply`. Requests the agent sent with a deadline and no answer are listed
under `### Awaiting replies`. See the [mail reference](/docs/reference/mail#the-prompt-block)
for the exact text.

## Producers

Every producer writes through the one `Send` operation, so the Inbox and Sent
views never miss a letter.

| Producer | Sender → recipient | Kind | Request or notice |
| --- | --- | --- | --- |
| Native Tasks notifications | the principal that caused it (the asker, the assigner, `system:workflow`; `system:tasks` when that principal can no longer send) → the agent or the customer | `task.assigned`, `task.question`, `task.answered`, `task.triage` | `task.question` is a request closed by the answer on the task; the others are notices |
| Goal reconciler | `system:goal` → the agent | `task.goal` | request: the reply is the agent's report on its Goal |
| Script results | `system:scripts` → the owning agent | `script.result` | request |
| Schedules | `system:schedule` → the schedule's recipient (default the owning agent) | `schedule.fire` unless the template names another | request unless the template sets `notice` |
| Request deadlines | `system:schedule` → the requester | `deadline`, `data.request_id` | notice |
| AI proxy budget | `system:proxy` → the agent | `budget.warn` | notice |
| Operator or Desktop | the customer, or `--as` another principal → anyone | `message` unless given | request unless `notice` |
| Agents | the calling agent → anyone, through `tmail` | sender's choice | sender's choice |
| Telegram | `plugin:telegram` → the mapped agent | `message` | request |
| Plugin workflow event | `plugin:<name>` → `queue:<prefix>` | plugin's choice | stored closed |

A request with a deadline sent by an agent arms a one-shot schedule keyed on
the request letter's id; the reply or archive that closes the request cancels
it in the same transaction. When the deadline passes first, the requesting
agent receives the `deadline` notice. A deadline on a request from any other
principal is stored but arms nothing.

### Goal delivery

The per-agent Goal reconciler sends `task.goal` with the selected task key and
the `selected` or `iteration_completed` reason. Its idempotency key includes
the agent, task key, task revision and terminal iteration identity, so recovery
and repeated scans do not duplicate a generation. An open Goal letter
suppresses another one; a dead one does not, and a positive per-agent cooldown
(60 seconds by default) still suppresses rapid repeats. The reconciler never
starts an iteration directly: the letter wakes the agent. Disabled agents or
disabled loops receive no new Goal letter.

### Task notifications

Task notifications are letters, and the task stays the source of truth:
mentions, waits and answers live on the task. A `task.question` letter is
answered on the task (`ttasks comment`, or the task drawer in the Desktop);
when the wait resolves, the tasks service closes the matching open question
letters with `close_note = task-comment:<id>`, for an agent recipient and the
customer alike. A workflow outcome that resolves the customer's open wait
closes its question letters with `task-outcome:<status>`.

## Groups

Group membership is the data `group:<name>` expands over; groups create no
mailboxes of their own. `tmail send --to group:dev-team` writes one letter to
each member except the sender, and a lead asks one member with
`tmail send --to agent:<member>`, with `--deadline` for a timed request. The
group tools that are not sends (`info`, `status`, `observe`, `loop`) are
unchanged.

## Queue triggers

A plugin that wants a workflow event to create a task sends a letter to
`queue:<prefix>`. That letter is stored closed and exists for ingress. A
trigger of queue `<prefix>` fires for a letter whose recipient is
`queue:<prefix>`, whose sender matches the trigger's `pattern` (a principal
glob such as `plugin:*` or `plugin:telegram`), and whose
`data.correlation_key` equals the trigger's correlation key when one is set.
The ingress reads the monotonic `mail.seq`. A letter to an agent never trips a
trigger. See [Task workflows](/docs/task-workflows#queue-triggers).

## Plugins

A plugin declares `mail: {send, receive}` in its manifest with the types
`mail-source` and `mail-sink`. It sends letters as `plugin:<name>` through
`POST /api/plugin/mail`, which answers `409 inbox_full` when the recipient's
inbox is at its cap. The plugin host drains the inbox of `plugin:<name>` like a
prompt drain, with the same attempt and dead-letter rules, calls the plugin's
`/deliver` with each letter, and closes it as `delivered` on success. The
drainer is woken after a committed send; a 5-second fallback timer retries
failed deliveries. A plugin receives only the letters addressed to it. See
[Plugins](/docs/plugins#mail).

The bundled Telegram process stays outside the daemon. It authorizes forum
updates and sends each one as a letter to the agent mapped to its topic. An
agent answers with `tmail reply`, which addresses `plugin:telegram`, and the
plugin's `/deliver` posts the reply to the topic of the sending agent.

## Live hints and the event hub

`GET /api/mail/ws` streams one frame per written letter, `{id, from, to, kind,
ts}`. A frame is only a refetch hint: the HTTP responses stay authoritative.
Nothing is replayed, because a client refetches on connect and on every
reconnect.

`GET /api/agent-states/ws` uses the same hint loop for agent state. It sends
`{agent, type, ts}` for every `iteration` and `state` event of any agent on
the host, so the UI refetches the agents list and the agent status. The loop
manager emits `state` when an agent is started or stopped, when its status line
changes, and when its loop halts or stops for idleness. The route
is not under `/api/agents/` because an agent may be named `ws`.

These sockets and the agent SSE stream `GET /api/agents/{name}/events` read
from one in-memory event hub. The hub never blocks a publisher: each
subscriber has a buffer of 64 events, and an event for a full buffer is
dropped. The hub gives every event a rising sequence number `seq` and counts
each drop in the OpenTelemetry counter `tariboy.events.dropped`. When a
subscriber that lost events has room again, the hub first sends it a `reset`
event with `data.dropped` set to the number of lost events. The SSE stream
writes each event as `id: <seq>` and `event: <type>`, so it forwards
`event: reset`. A hint socket closes with status 1013 (try again later) on a
reset; the client reconnects and refetches, which recovers what it missed.
The hub keeps no history, so neither stream replays the lost events.

## Audit

Mail writes the audit events `mail_sent`, `mail_answered`, `mail_closed`,
`mail_dead`, `mail_requeued` and `mail_cleared` to the agent's audit log.
