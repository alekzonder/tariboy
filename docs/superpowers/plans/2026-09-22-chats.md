# Chats Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the channel-projection chat with a first-class chat entity — identity, kind, participants, delivery, replies, an unanswered-message queue, and live events — without changing how an agent is woken.

**Architecture:** Chats are a thin layer over the existing bus. `messages`, `subscriptions` and `deliveries` are untouched; a chat is a row that owns exactly one transport channel `chat:<id>` plus a participant list. An agent participant materializes a locked subscription to that channel, so `Publish -> delivery -> WakeMessage` and `HasPending` keep working unchanged. Message rows are never rewritten: a migrated personal chat reads its pre-migration history through the existing `chatRowsSQL` projection behind a `legacy_agent` column.

**Tech Stack:** Go 1.26, SQLite via `internal/store`, the `registry.Command` surface that emits both CLI and HTTP routes, `coder/websocket`, React/TypeScript with Vitest.

**Spec:** `docs/superpowers/specs/2026-09-22-chats-design.md`, approved in IMPROVE-99bk comment #3138.

## Review Focus

Five input classes the spec implies but that no task's headline behaviour exercises. Each line's test is added to the task that owns the code.

- **A chat id that collides with a reserved prefix or an existing channel.** Creating a chat with id `dm:worker`, `telegram:worker` or a slug whose channel already exists must be rejected with a user error, not silently take over another chat's channel. Test in Task 7.
- **A participant removed while unprocessed deliveries remain.** Removing an agent participant unsubscribes it; its already-created, unacked deliveries must stay pending and still render, never vanish. Test in Task 3.
- **A reply whose original lives on a non-chat channel.** `group:<g>:direct:<agent>` requests and plugin sink messages have no chat, so `replyTarget` must fall through to the existing inbox and origin rules unchanged. Test in Task 3.
- **An answer published as a plain send instead of a reply.** A plain chat send fills no `in_reply_to`, so the original stays in the unanswered queue. That is intended; the test pins it so a later "helpful" fallback cannot quietly mark it answered. Test in Task 4.
- **A message that arrives between render and read-mark.** `read_ts` moves forward only, and a second window marking an older timestamp must not resurrect read messages. Test in Task 2.

```sql
-- 0044_chats.sql — chats as a first-class entity over the existing bus.
-- messages/subscriptions/deliveries are untouched: a chat owns one channel.
CREATE TABLE chats (
    id           TEXT PRIMARY KEY,
    kind         TEXT NOT NULL,
    title        TEXT NOT NULL DEFAULT '',
    channel      TEXT NOT NULL UNIQUE,
    legacy_agent TEXT,
    created_at   TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
    archived_at  TEXT
);

CREATE TABLE chat_participants (
    chat_id   TEXT NOT NULL,
    principal TEXT NOT NULL,
    role      TEXT NOT NULL DEFAULT 'member',
    joined_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
    read_ts   TEXT NOT NULL DEFAULT '',
    muted     INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (chat_id, principal)
);
CREATE INDEX idx_chat_participants_principal ON chat_participants(principal);
```

- [ ] **Step 5: Write `internal/bus/chats.go`**

Plain CRUD over the two tables plus reconciliation. `ReconcileChats` runs at daemon startup exactly as the existing inbox-subscription repair does, so a persisted agent created before this migration gets its chats on the next start.

```go
// ChatChannelFor is the one transport channel a chat owns. It is deliberately
// never an agent inbox: the bus suppresses an author's own delivery only on
// NON-inbox channels, so an inbox-backed chat would echo an agent's own reply
// back into its own queue.
func ChatChannelFor(id string) string { return "chat:" + id }

// ReconcileChats provisions the per-agent chats and their participants. Safe to
// re-run: every write is an upsert keyed by the chat id.
func (b *Bus) ReconcileChats(agents []string, customer string) error {
	for _, a := range agents {
		seeds := []struct{ id, kind, title, customerRole string }{
			{"dm:" + a, "direct", a, "member"},
			{"tasks:" + a, "tasks", a + " tasks", "member"},
			{"service:" + a, "service", a + " service", "observer"},
		}
		for _, seed := range seeds {
			if err := b.upsertChat(Chat{
				ID: seed.id, Kind: seed.kind, Title: seed.title,
				Channel: ChatChannelFor(seed.id), LegacyAgent: legacyFor(seed.kind, a),
			}); err != nil {
				return err
			}
			if err := b.upsertParticipant(seed.id, "agent:"+a, "member"); err != nil {
				return err
			}
			if err := b.upsertParticipant(seed.id, customer, seed.customerRole); err != nil {
				return err
			}
		}
	}
	return nil
}

// legacyFor marks only the personal chat as carrying pre-migration history:
// that history is the two merged inboxes, which is what chatRowsSQL reads.
func legacyFor(kind, agent string) string {
	if kind == "direct" {
		return agent
	}
	return ""
}
```

- [ ] **Step 4: Implement `ChatFeed`**

Select from the chat's own channel and, when `LegacyAgent` is set, union the existing projection so no pre-migration message is lost. Keep the existing newest-page-then-reverse shape and the rule that `before` is a timestamp: a union of two channels still does not sort by id.

```go
func (b *Bus) ChatFeed(chat Chat, types []string, limit int, before string) ([]Message, error) {
	if limit <= 0 {
		limit = 200
	}
	filter, filterArgs := typeFilterSQL(types)
	inner := `SELECT ` + messageColumns + ` FROM messages WHERE channel = ?`
	args := []any{chat.Channel}
	if chat.LegacyAgent != "" {
		// Pre-migration history is the two merged inboxes; chatRowsSQL already
		// resolves them and is already tested.
		inner += ` UNION ALL SELECT ` + messageColumns + ` FROM (` + chatRowsSQL + `) WHERE agent = ?`
		args = append(args, b.customer, b.customer, b.customer, b.customer, b.customer, chat.LegacyAgent)
	}
	args = append(args, filterArgs...)
	page := ""
	if before != "" {
		page = " AND ts < ?"
		args = append(args, before)
	}
	rows, err := b.db.Query(`SELECT `+messageColumns+` FROM (`+inner+`) WHERE `+filter+page+
		` ORDER BY ts DESC, id DESC LIMIT ?`, append(args, limit)...)
	if err != nil {
		return nil, err
	}
	msgs, err := scanMessages(rows)
	if err != nil {
		return nil, err
	}
	for i, j := 0, len(msgs)-1; i < j; i, j = i+1, j-1 {
		msgs[i], msgs[j] = msgs[j], msgs[i]
	}
	return msgs, nil
}
```

- [ ] **Step 5: Make `replyTarget` chat-aware**

```go
// replyTarget resolves the channel a reply to m lands on:
//  1. explicit reply_to — the override external sinks (Telegram) rely on;
//  2. the chat that owns m's channel — a conversation answer belongs in the
//     conversation, which is also what makes a multi-agent chat possible;
//  3. the source agent's inbox;
//  4. the originating channel.
func (b *Bus) replyTarget(x dbtx, m Message) (string, error) {
	if m.ReplyTo != "" {
		return m.ReplyTo, nil
	}
	chat, ok, err := chatByChannel(x, m.Channel)
	if err != nil {
		return "", err
	}
	if ok {
		return chat.Channel, nil
	}
	if strings.HasPrefix(m.Source, "agent:") {
		return m.Source + ":inbox", nil
	}
	return m.Channel, nil
}
```

Call it inside `Reply`'s existing transaction so the lookup sees the same snapshot as the publish.

- [ ] **Step 6: Implement participant subscription materialization**

```go
func (b *Bus) AddParticipant(chatID, principal, role string) error {
	chat, err := b.GetChat(chatID)
	if err != nil {
		return err
	}
	if err := b.upsertParticipant(chatID, principal, role); err != nil {
		return err
	}
	// Only an agent participant needs a delivery queue: the customer reads over
	// HTTP. This is what keeps Publish -> delivery -> wake unchanged.
	if name, ok := strings.CutPrefix(principal, "agent:"); ok {
		if _, err := b.SubscribeLocked(name, chat.Channel, nil, nil); err != nil {
			return err
		}
	}
	return nil
}

func (b *Bus) RemoveParticipant(chatID, principal string) error {
	chat, err := b.GetChat(chatID)
	if err != nil {
		return err
	}
	if _, err := b.db.Exec(`DELETE FROM chat_participants WHERE chat_id=? AND principal=?`,
		chatID, principal); err != nil {
		return err
	}
	// Deliveries already created are that agent's outstanding work: leaving the
	// chat does not erase a message it was asked to handle.
	if name, ok := strings.CutPrefix(principal, "agent:"); ok {
		if _, err := b.UnsubscribeChannel(name, chat.Channel); err != nil {
			return err
		}
	}
	return nil
}
```

`SubscribeLocked` is `Subscribe` with `locked=1`, so the operator unsubscribe path treats a chat membership the way it already treats an inbox or group subscription.

```go
	SELECT ` + messageColumns + `
	FROM messages m
	JOIN chats c ON c.channel = m.channel
	JOIN chat_participants p ON p.chat_id = c.id AND p.principal = ?
	WHERE c.id = ?
	  AND (` + fromSQLFor("m") + `) <> ?
	  AND m.ts >= p.joined_at
```
