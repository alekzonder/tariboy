# Mailbox Implementation Plan

> **For agentic workers:** This plan is executed through Tariboy queues, not
> in one session. Each task below is one task in the DEV queue (development
> workflow, pool `developers`) or the TASK queue (`tariboy-image-creator`),
> and one pull request. The developer who takes a DEV task writes its own
> step-level plan in the workflow's `plan` status from the task description,
> the spec and this document; the tech lead approves it in `approval`. Steps
> here use checkbox (`- [ ]`) syntax for the tech lead's tracking.

**Goal:** Replace the channel bus and chats with one per-principal mailbox
that keeps every current wake, notification and plugin flow working, with
`tmail` for agents, `tariboy mail` for operators and Mailbox tabs in the
Desktop.

**Architecture:** One `mail` table, one row per recipient, carries every
message. `internal/mail` replaces `internal/bus` behind the same wake hook,
prompt drain and event hints. Requests are closed by a reply, notices by a
read. Producers (Native Tasks, Goal, scripts, schedules, proxy, groups,
Telegram) call `Send` instead of `Publish`. The Desktop and the store skills
move to the new API and CLI in follow-up tasks that start when the core is in
review.

**Tech Stack:** Go (daemon, CLI, SQLite migrations), React + TypeScript
(Desktop), Starlight docs, store skills and images in `~/github/tariboy-store`.

**Spec:** `docs/superpowers/specs/2026-10-26-mailbox-design.md`. Every task
argues from it; developers read the spec first and this plan second.

## Global Constraints

- Every current flow keeps waking the agent: task notifications, Goal,
  script results, schedule alarms, request deadlines, group letters,
  Telegram. (spec: Anti-goals)
- No data migration: the migration drops `channels`, `messages`,
  `subscriptions`, `deliveries`, `chats`, `chat_participants`,
  `task_notification_state` and creates `mail`. (spec §1)
- Attempt limit 5, inbox cap from `messages_max_queue`, batch from
  `messages_batch`; both agent fields keep their names, API fields and
  compose keys. (spec §1, §3)
- A reply is a notice unless marked `--ask`; a `task.question` letter cannot
  be answered by mail (`answer_on_task`). (spec §1, §2)
- `tmail` mirrors `ttasks`: agent mode on `TARIBOY_TOOLS_SOCKET` via
  `/tools/mail/<action>`, operator mode otherwise; `tariboy mail` is the same
  client in operator mode. (spec §3)
- The image contract accepts plugin `messages` and runtime placeholders
  `messages` / `awaiting-replies` as aliases of `mail`. (spec §3)
- `AGENTS.md`: typed results with `registry.WithResult[T]` and a
  `typedCallSets` entry; `internal/commands/testdata/openapi.json` and
  `ui/src/lib/api-types.generated.ts` regenerated in the same pull request;
  `make check` green; docs updated in the same task; no attribution
  trailers; linear history; isolated `TARIBOY_BASE_DIR` /
  `TARIBOY_RUNTIME_DIR` for every test daemon.
- Version is not bumped by any task; release tooling bumps minor.

## Review Focus

Behaviours the spec implies that no task's happy path exercises, most likely
to bite first. Each has its test pinned in the owning task.

1. **Group letter from a member.** `tmail send --to group:dev` by a member
   must reach every other member and not the sender; an empty expansion is
   an error, not a silent no-op. (Task 1, `TestSendGroupExpandsWithoutSender`)
2. **Failed iteration keeps notices.** A notice rendered into an iteration
   that errors, times out or is killed stays open, is rendered again, and
   dead-letters after five renders. (Task 1,
   `TestNoticeStaysOpenAfterFailedIteration`)
3. **Inbox cap counts open letters only.** Closed letters never count; a
   letter stored dead with `queue_limit` fires no wake and the Telegram
   route answers `409 inbox_full`. (Task 1, `TestSendAtCapStoresDeadWithoutWake`)
4. **Customer login adoption.** After `customer_login` changes, letters to
   and from the old `user:<x>` are rewritten and the Desktop unread count
   follows the new principal. (Task 1, `TestAdoptCustomerRewritesMail`)
5. **Question answered on the task closes the agent's letter too.** When an
   agent's `task.question` wait resolves, the letter in the asked agent's
   inbox closes with `task-comment:<id>`; the Desktop badge for the customer
   drops the same way. (Task 1, `TestWaitResolutionClosesQuestionLetters`;
   Task 2, `questionBadgeDropsWhenLetterCloses`)

## Process

### Queues and roles

| Who | Does |
| --- | --- |
| Tech lead (this session) | writes spec and plan on branch `mailbox-design`; creates and starts queue tasks; approves or returns developer plans; answers task questions; watches review; never edits product code |
| DEV developers pool | plans and implements Tasks 1–3, one pull request each; the workflow auto-merges (`AUTO_MERGE=true`) when checks pass |
| `tariboy-image-creator` (TASK queue) | Tasks 4–5 in `~/github/tariboy-store`, one pull request each, through its own delivery skill |

### Sequencing

```
Task 0 (lead)   spec + plan PR merged to main
Task 1 (DEV)    mail core ──────────────┐ reaches review
                                        ├─> Task 2 (DEV) Desktop
                                        ├─> Task 3 (DEV) docs      (max 2 DEV tasks past backlog)
                                        └─> Task 4 (TASK) store skills ──> Task 5 (TASK) images + workflows
```

At most two DEV tasks are past `backlog` at any moment. Task 1 runs alone
until it reaches `review`; then Task 2 and Task 3 start. Task 4 starts when
Task 1 reaches `review` (the `tmail` help is then final); Task 5 after Task 4
merges. A release built by `tariboy-release-publisher` after Tasks 1–3 merge
and installed by the customer brings the mailbox to this host; the pool
agents keep working through the `messages` alias until then and are moved to
rebuilt images last, after Task 5 is verified against the released daemon.

### Tech lead runbook

- [ ] **Task 0.** Open the pull request for branch `mailbox-design` (spec and
  this plan), wait for checks, rebase-merge it. The DEV tasks reference the
  two files by path on `main`.
- [ ] Create DEV tasks 1–3 from the descriptions below with
  `tariboy tasks create --queue DEV --title ... --description "$BODY"`; reuse
  `DEV-5bzj` ("? mailbox") as Task 1 by updating its title and description.
  Create TASK tasks 4–5 with `--queue TASK` and assign them to
  `tariboy-image-creator` when their turn comes.
- [ ] Start Task 1: `tariboy tasks advance KEY --from backlog --outcome start`.
- [ ] When a task reaches `approval`, read `tariboy tasks artifacts show KEY plan`.
  Approve when it covers its acceptance list below and its interfaces match
  this plan; otherwise `changes_requested` with the exact deltas.
- [ ] When Task 1 reaches `review`: start Task 2 and Task 3; assign Task 4.
- [ ] Watch the review state with `tariboy tasks list --queue DEV --json`
  and `tariboy tasks workflow get KEY`; answer `ttasks ask` questions on the
  task within the session; resume `holder_unavailable` pauses with
  `--decision release`.
- [ ] After Tasks 1–3 merge, request a release: create a TARI task for
  `tariboy-release-publisher` asking for the next minor version with the
  mailbox as its headline change. The customer approves the exact version on
  that task (the publisher never releases without it) and installs the
  release on this host themselves. Merging code does not change the running
  daemon; until the release is installed, the host daemon has no
  `/tools/mail`, no `mail` capability and no `tmail`.
- [ ] After Task 4 merges, start Task 5. Its pull request may merge before
  the release is installed, but its smoke check (an agent from a rebuilt
  image renders the letters block and finds `tmail`) and the move of the pool
  agents to the rebuilt images wait for the installed release.
- [ ] After Task 5 is verified on the released daemon, close the project
  with a summary comment on `DEV-5bzj`.

**Interfaces (produced; Tasks 2–4 depend on these exactly):**

Letter JSON, returned by every API and tool route and by `tmail --json`:

```json
{"id":"m-20261026T104200Z-000007","seq":7,"from":"user:customer","to":"agent:worker",
 "subject":"Re: TARI-42","body":"...","kind":"message","data":{},
 "needs_reply":true,"in_reply_to":"m-...","deadline":"","created_at":"2026-10-26T10:42:00.000000000Z",
 "read_at":"","answered_at":"","answer_id":"","close_note":"",
 "attempts":1,"dead_at":"","dead_reason":"","produced_in_iteration":""}
```

Operator commands (result struct → route):

| Command | Route | Result |
| --- | --- | --- |
| `mail.ls` | `GET /api/mail?box=inbox\|sent\|archive&as=&limit=&before=` | `MailList{box, as, letters[], count, next_before}` |
| `mail.show` | `GET /api/mail/{id}?as=` | `MailThread{letter, reply?}` |
| `mail.send` | `POST /api/mail` `{to, subject, text, kind?, data?, deadline?, notice?, as?}` | `MailSendResult{letters[]}` |
| `mail.reply` | `POST /api/mail/{id}/reply` `{text, ask?, as?}` | `MailReplyResult{letter, closed}` |
| `mail.close` | `POST /api/mail/{id}/close` `{note?, as?}` | `MailCloseResult{letter}` |
| `mail.read` | `POST /api/mail/read` `{ids[], as?}` | `MailReadResult{closed_notices, read}` |
| `mail.requeue` | `POST /api/mail/{id}/requeue` `{as?}` | `MailRequeueResult{letter}` |
| `mail.unread` | `GET /api/mail/unread?as=` | `MailUnread{as, open, unread, by_sender:[{sender, kind, count}]}` |
| `agent.mail.clear` | `POST /api/agents/{name}/mail/clear` | `MailClearResult{deleted}` |

`as` defaults to `user:<customer_login>`. Errors: `unknown_recipient`,
`empty_group`, `forbidden` (reply or read by a non-recipient),
`answer_on_task` (reply to `task.question`; message names
`ttasks comment <key>`), `inbox_full` (plugin route only), `not_found`.

Agent tools, all `POST /tools/mail/<action>` with a JSON body, sender fixed
to the calling agent: `inbox {all?}`, `sent`, `archive`, `show {id}`,
`send {to, subject, text, kind?, data?, deadline?, notice?}`,
`reply {id, text, ask?}`, `requeue {id}`. Gated by capability `mail`.

`tmail` commands exactly as the spec's table in §3; `tmail --help-json`
follows `ttasks`. `tariboy mail <cmd>` is operator mode.

Live hints: `GET /api/mail/ws`, frame `{id, from, to, kind, ts}`.

Plugin API: `POST /api/plugin/mail` `{to, subject, text, kind?, data?,
notice?, idempotency_key?}` → `{letters[]}` or `409 inbox_full`; `/deliver`
body `{letter}`; manifest `mail: {send, receive}`, types `mail-source` /
`mail-sink`.

Audit events: `mail_sent`, `mail_answered`, `mail_closed`, `mail_dead`,
`mail_requeued`, `mail_cleared`.

Prompt block text: exactly spec §3 ("Requests: answer each one…",
"Notices: read them; they close when this iteration finishes.").
