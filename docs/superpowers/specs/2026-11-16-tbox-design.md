# tbox: запуск образов агентов в обычных сессиях harness

Статус: на согласовании. Дата: 2026-11-16.

Пометка «(решение автора)» стоит у решений, которые принял составитель
документа, а не заказчик. Их можно менять при проверке.

## Зачем

- Иногда нужно использовать образ или скиллы образа в обычной сессии Claude
  Code, Codex или OpenCode. Сейчас это невозможно: образ запускает только
  демон tariboy.
- Tariboy трудно распространять целиком. `tbox` даёт привычный вход: человек
  запускает свой harness с образом, а автономность (демон, почта, задачи)
  добавляет позже, когда она нужна.

## Что это

`tbox` — отдельный бинарник без демона. Он:

1. подключает источники (Stores) с образами, скиллами и промтами;
2. собирает самодостаточный образ из `Tariboyfile.yaml`;
3. запускает сессию harness с промтом и скиллами образа;
4. внутри этой сессии показывает агенту только скиллы образа.

## Цели

- `tbox run <образ> <harness>` запускает обычную интерактивную сессию harness.
  Промт образа передан как инструкции harness, скиллы образа видны harness
  нативно.
- Собранный образ самодостаточен: все скиллы и промты лежат в архиве. Архив
  можно перенести на другую машину и запустить без сети и без Stores.
- Архив имеет тот же формат, что архив образа tariboy schema v2. Образ,
  собранный в `tbox`, импортируется в tariboy.
- Любой человек выполняет `tbox store add <имя> <источник>` и собирает образ
  из этого Store. Имена других Stores для сборки не нужны.
- Интерактивный режим: выбор образа и harness, затем запуск.
- Конструктор: собрать образ из выбранных скиллов и промтов.

## Не цели

- Демон, цикл итераций, почта, задачи, цели, AI-прокси, tmux, бюджет.
- Плагины tariboy и runtime-вставки. `tbox` их игнорирует и ничего не
  подставляет взамен.
- MCP-серверы в образе. Это следующий вид содержимого Store; он требует
  изменения формата архива.
- Workflows из Store.
- Нативная доставка скиллов в Cursor CLI. Для него остаётся запасной путь.
- Поддержка `schema_version: 3` в tariboy. Это отдельная задача после первого
  этапа `tbox`.
- Изоляция от глобальных скиллов пользователя. Они остаются видны harness
  рядом со скиллами образа.

## Анти-цели

- `tbox` импортирует пакет tariboy или требует работающий демон.
- `tbox` пишет что-либо в рабочую директорию пользователя (`.claude`,
  `.agents`, `.codex`, `.opencode`).
- `tbox` изменяет основной `config.toml` Codex или настройки Claude и OpenCode
  пользователя.
- Сборка образа из Store падает, потому что у пользователя нет другого Store
  с определённым именем.
- Образ, собранный в `tbox`, отвергается при импорте в tariboy.

## Ограничения

- Код лежит в каталоге `tbox/` этого репозитория со своим `go.mod`. Ни один
  файл в `tbox/` не импортирует `github.com/.../tariboy/...`. Разбор
  Tariboyfile, проверка скиллов и упаковка архива написаны в `tbox` заново.
- Язык Go, один статический бинарник (решение автора).
- Node.js и `npx` не нужны. Git-источники читает системный `git`.
- Тесты не обращаются к `~/.tbox`, `~/.codex`, `~/.claude`, конфигурации
  OpenCode и к живому tariboy. Каждый тест задаёт свои `TBOX_HOME`,
  `CODEX_HOME`, `OPENCODE_CONFIG_DIR`.
- `tbox` имеет свою версию, независимую от версии tariboy (решение автора).
- Спецификации, планы и код `tbox` ведутся в отдельной ветке `dev/tbox` и в
  отдельном worktree `.worktrees/tbox`, не в основном рабочем дереве.

## Подходы

Общая схема одна: в центре образ. Ядро собирает архив из каталога с
`Tariboyfile.yaml`, хранит его и запускает. Stores и конструктор — слои
сверху. Вариант «запускать прямо из источников без сборки» отклонён: он
нарушает самодостаточность.

Внутри схемы были такие выборы.

| Вопрос | Выбрано | Отклонено | Почему |
| --- | --- | --- | --- |
| Где живёт код | `tbox/` в этом репозитории, свой `go.mod` | Отдельный репозиторий; тот же модуль с `cmd/tbox` | Импорт tariboy невозможен технически, а тест совместимости лежит рядом с обеими реализациями |
| Получение скиллов | Своя реализация: git, https-архив, директория | Вызов `npx skills` | Нет зависимости от Node; поддержаны https-архивы и произвольный ref |
| Адрес скилла в образе | Полный адрес источника в Tariboyfile, schema v3 | Tariboyfile v2 плюс `skills-lock.json`; имена локальных Stores | Один файл, пишется руками, не зависит от того, какие Stores подключены |
| Части только для tariboy | Поле `only: tariboy` в v3; `tbox` не кладёт их в архив | Отбрасывать по совпадению имени с плагином; оставлять всё; отказывать в запуске | Явная разметка автора вместо догадок |
| Codex | Плагин в кэше `$CODEX_HOME` и файл профиля, запуск `codex --profile` | Свой `CODEX_HOME` у `tbox`; каталог скиллов в промте; `.agents/skills` в проекте | Скиллы нативны, авторизация и история остаются пользователя, основной `config.toml` не меняется |
| Промт в сессии | Инструкции harness | Первое сообщение пользователя | Сессия открывается пустой и ждёт пользователя; промт переживает сжатие контекста |
| Пересборка | Только при изменении содержимого, по отпечатку исходника; версия не важна | Каждый раз; строгий отказ при той же версии, как в tariboy | Цикл «поправил — запустил» без лишних шагов и без лишних сборок |
| Интерактив | Простые списки с выбором стрелками | Полноэкранный интерфейс | Меньше кода; содержимое показывает `tbox skill <имя>` |

## Понятия

- **Store** — именованный источник: git-репозиторий, https-архив или
  директория. В нём можно посмотреть и выбрать образы, скиллы и промты. Имя
  Store нужно только в командах пользователя.
- **Исходник образа** — каталог с `Tariboyfile.yaml`.
- **Образ** — собранный архив с манифестом, промтами и копиями скиллов.
- **Каталог запуска** — распакованный образ плюс файлы, сгенерированные для
  конкретного harness.

## Раскладка на диске

Корень — `$TBOX_HOME`, по умолчанию `~/.tbox`.

```
~/.tbox/
  stores.json                       # имя → источник, ref
  stores/<имя>/                     # клон git или распакованный архив
  cache/sources/<хеш адреса>/       # кэш удалённых скиллов и промтов
  images/<имя>/refs/<digest>.tar.gz # собранные образы
  images/<имя>/tags/<тег>           # указатель на digest
  run/<digest>/<harness>/           # каталог запуска
  sources/<имя>/                    # исходники, созданные конструктором
```

Раскладка `images/` повторяет хранилище tariboy (`refs` и `tags`), чтобы
правила тегов и `latest` были теми же.

## Stores

```
tbox store add <имя> <источник> [--ref REF]
tbox store list
tbox store show <имя>
tbox store refresh <имя>
tbox store ref <имя> <REF>
tbox store remove <имя>
```

| Источник | Что делает `add` | Что делает `refresh` |
| --- | --- | --- |
| git: HTTPS, SSH, `owner/repo` (GitHub) | клонирует в `stores/<имя>/` | получает изменения по выбранному ref |
| https-архив `.tar.gz` или `.zip` | скачивает и распаковывает | скачивает заново |
| директория, относительная или абсолютная | запоминает абсолютный путь, читает на месте | перечитывает |

Содержимое Store:

- образы: `images/<имя>/Tariboyfile.yaml`;
- скиллы: `skills/<имя>/SKILL.md`. Если каталога `skills/` нет, `tbox` ищет
  `SKILL.md` в известных местах: корень, `.agents/skills/`, `.claude/skills/`
  (решение автора; точный список — за исполнителем, ориентир — `npx skills`);
- промты: `prompts/*.md`.

`workflows/` и прочее `tbox` не читает и не считает ошибкой. Один неверный
образ или скилл показывается с ошибкой и не скрывает остальные.

Правила безопасности те же, что у Stores в tariboy: `git` вызывается массивом
аргументов с ограничением по времени; адрес с учётными данными отвергается;
ref с пробелом, с `..` или с ведущим `-` отвергается; селектор не выходит за
каталог Store, в том числе через симлинк. Архив распаковывается без симлинков
и без путей наружу, с пределом размера.

## Tariboyfile schema v3

`tbox` собирает `schema_version: 3` и `schema_version: 2`. Tariboy пока
понимает только v2.

```yaml
schema_version: 3
image_version: 0.1.0
extends:
  - ../base
plugins:
  - name: mail
skills:
  - git: https://github.com/obra/superpowers
    path: skills/brainstorming
    ref: v5.0.0
  - url: https://example.com/some-skill.tar.gz
  - dir: ./skills/developer-mode
  - dir: ../../skills/mail
    only: tariboy
prompts:
  - file: ./instructions.md
  - git: https://github.com/company/prompts
    path: process/review.md
  - file: ./tariboy-process.md
    only: tariboy
  - runtime: workdir
  - runtime: messages
```

Отличия от v2:

- Запись скилла — ровно одно из `dir`, `git`, `url`. Для `git` обязателен
  `path`, необязателен `ref` (ветка, тег или коммит; без него — ветка по
  умолчанию). `url` — https-архив, в корне которого лежит скилл.
- Запись промта — ровно одно из `file`, `git`, `url`, `runtime`. Для `git`
  обязателен `path`. `url` — один Markdown-файл.
- Необязательное поле `only` у скилла и у промта. Единственное допустимое
  значение — `tariboy`. Без поля запись участвует везде.
- `extends`, `plugins`, `image_version`, `ROLE.md`, пределы (128 скиллов, 1024
  промта, размеры файлов), правила имён скиллов и запрет симлинков — как в v2.
  Источник правил: `internal/imagefile`, `internal/agentskills` и
  `docs/docs/images/index.mdx`.

Для v2 `tbox` дополнительно читает `skills-lock.json` рядом с Tariboyfile и в
корне Store и восстанавливает `.agents/skills/` сам, во временном каталоге
сборки, не меняя Store. Он поддерживает источники `github` (`source` плюс
`skillPath`) и `local` и считает `computedHash` тем же алгоритмом, что
`internal/stores/skillslock.go`. Lock-файл v2 не хранит коммит, поэтому
`tbox` берёт ветку по умолчанию. Несовпадение хеша — предупреждение с именем
скилла, а не ошибка (решение автора): ручная сборка в tariboy хеш тоже не
проверяет, и иначе образ собирался бы в tariboy, но не в `tbox`.

### Что `tbox` делает с частями для tariboy

- Скилл или промт с `only: tariboy` не попадает в архив.
- `plugins` допустимы и не исполняются. В манифест архива `tbox` пишет пустой
  список плагинов (решение автора): иначе tariboy при импорте потребует
  скиллы плагинов, которых в архиве нет.
- Runtime-вставки `tbox` игнорирует все: в архив они не попадают, и `tbox`
  ничего не подставляет вместо них. Промт в сессии — это только статические
  промты образа. Дополнительная причина не класть вставки в архив: tariboy
  при импорте требует для каждой вставки её плагин
  (`internal/imagecontract/contract.go:52-54`, `:105`), а плагин требует свой
  скилл (`:119`).
- Путь `$PLUGINS/...` в `dir` или `file` `tbox` разрешить не может: каталога
  плагинов у него нет. В v3 такая запись допустима только с `only: tariboy`.
  В v2 сборка завершается с ошибкой, которая называет запись (решение
  автора).
- Образ v2 не размечен. `tbox` собирает и запускает его целиком и печатает
  предупреждение, если образ объявляет плагины: часть скиллов в нём
  рассчитана на демон.

Следствие: из одного исходника с пометками `tbox` и tariboy соберут разные
архивы. Это ожидаемо.

## Сборка

```
tbox build <store>/<образ> [--name ИМЯ] [--tag ТЕГ]
tbox build --path <каталог> [--name ИМЯ] [--tag ТЕГ]
tbox images                    # собранные образы и образы в Stores
tbox image show <образ>        # манифест, скиллы, промты
tbox image rm <образ>[:тег]
tbox image export <образ>[:тег] [-o файл]
tbox image import <файл>
```

Шаги сборки:

1. Разобрать Tariboyfile, развернуть `extends` (правила слияния как в v2).
2. Получить каждый удалённый скилл и промт в `cache/sources/`. Локальные
   читать на месте.
3. Проверить каждый скилл и набор скиллов по правилам tariboy.
4. Записать `tbox-lock.json` рядом с Tariboyfile: для каждой удалённой записи
   — адрес, коммит (для git) и хеш содержимого. Если файл уже есть, сборка
   берёт коммиты из него; `tbox build --update` обновляет их (решение автора).
   Для Store-директории, доступной только на чтение, lock пишется в
   `$TBOX_HOME` (решение автора).
5. Записать архив tariboy schema v2: `manifest.json`, `prompt/template.json`,
   `prompt/layers/*`, `skills/<имя>/**`. Формат и digest — по
   `internal/image/build_v2.go` и `internal/image/content_digest.go`.
6. Опубликовать под тегом `image_version` и под `latest`.

### Пересборка только при изменении

Сборка выполняется, только если исходник изменился. Номер `image_version` на
это не влияет.

- Перед сборкой `tbox` считает отпечаток исходника: хеш от Tariboyfile, слоёв
  `extends`, всех локальных файлов скиллов и промтов, которые войдут в образ,
  и записей `tbox-lock.json` для удалённых. Записи с `only: tariboy` в
  отпечаток не входят.
- Отпечаток последней сборки хранится рядом с образом в `$TBOX_HOME`, не в
  архиве. Совпал — сборки нет, используется готовый образ.
- Проверка не обращается к сети: удалённые записи представлены коммитом и
  хешем из lock-файла. Новые коммиты подтягивает только `tbox build --update`
  или `tbox store refresh`.
- Проверка должна быть быстрой: заметно быстрее сборки и незаметной при
  запуске. Способ (например, пропуск файлов с прежними размером и временем
  изменения) — за исполнителем.
- Если отпечаток изменился при том же `image_version`, теги версии и
  `latest` переходят на новую сборку, и `tbox` сообщает об этом одной
  строкой. Ошибки, как в tariboy, нет. Прежний архив остаётся в `refs/`, пока
  его не удалит `tbox image rm` или `tbox clean`.

`export` и `import` используют конверт `tariboy-portable`
(`internal/portablearchive`), чтобы файл принимал `tariboy image import`, а
`tbox` принимал экспорт tariboy (решение автора).

Образ, импортированный из tariboy, может содержать runtime-вставки и скиллы
плагинов. `tbox run` обращается с ним как с образом v2: запускает целиком,
пропускает неподдержанные вставки и предупреждает.

## Запуск

```
tbox run <образ> <harness> [-- аргументы harness]
tbox run                      # интерактивный выбор
tbox clean [<образ>]          # убрать каталоги запуска и файлы в $CODEX_HOME
```

`<образ>` — имя собранного образа с необязательным тегом (`developer`,
`developer:0.3.0`) или селектор Store (`tariboy/developer`). Для селектора
`tbox` проверяет отпечаток исходника и пересобирает образ, только если он
изменился (см. «Пересборка только при изменении»).
`<harness>` — `claude`, `codex` или `opencode`.

Шаги:

1. Распаковать образ в `run/<digest>/<harness>/image/`, если этого ещё нет.
2. Склеить промт: статические слои по порядку шаблона, без добавлений.
   Runtime-вставки в шаблоне (они есть в образах, импортированных из tariboy)
   пропускаются. Записать в `run/<digest>/<harness>/PROMPT.md`.
3. Сгенерировать файлы для harness (таблица ниже).
4. Запустить harness в текущей директории и в текущем терминале: `tbox`
   заменяет себя процессом harness. В окружение добавляются
   `TBOX_IMAGE_DIR=<каталог запуска>/image` и `TBOX_IMAGE=<имя>:<тег>`.
   Аргументы после `--` передаются harness без изменений.

| Harness | Скиллы | Промт | Что пишется вне `$TBOX_HOME` |
| --- | --- | --- | --- |
| Claude Code | сгенерированный плагин (`.claude-plugin/plugin.json` плюс `skills/`), флаг `--plugin-dir` | `--append-system-prompt-file` | ничего |
| Codex | плагин в `$CODEX_HOME/plugins/cache/tbox/<образ>/<версия>/` | файл профиля | кэш плагина и `$CODEX_HOME/tbox-<образ>.config.toml` |
| OpenCode | `OPENCODE_CONFIG_DIR=<каталог запуска>` с `opencode.json`, где `skills.paths` указывает на скиллы образа | `instructions` в том же `opencode.json` | ничего |

Что проверено на установленных версиях (Codex 0.166.0, OpenCode 1.19.5,
Claude Code 2.1.325) в изолированных каталогах:

- Codex: плагин с `.codex-plugin/plugin.json` и `skills/`, лежащий в кэше, и
  конфигурация с `[marketplaces.tbox]` и `[plugins."demo@tbox"] enabled = true`
  дают скилл `demo:hello-tbox` в промте модели (`codex debug prompt-input`).
- Codex: та же конфигурация в `$CODEX_HOME/<имя>.config.toml` работает с
  `codex --profile <имя>`. Без флага скилл не виден. Файл профиля вне
  `$CODEX_HOME` отвергается. Включение плагина через `-c` не работает.
- OpenCode: `skills.paths` в `opencode.json` из `OPENCODE_CONFIG_DIR`
  добавляет скилл в `opencode debug skill`.
- Claude Code: `--plugin-dir` уже используется в tariboy
  (`internal/harness/skills.go`); флаги `--append-system-prompt[-file]` есть в
  `claude --help`.

Что исполнитель проверяет сам, до кода соответствующего адаптера:

- Codex: каким ключом профиля задаются инструкции (кандидаты —
  `developer_instructions`, `model_instructions_file`), и нужна ли запись
  `[marketplaces.tbox]` или достаточно кэша и `[plugins]`.
- OpenCode: сохраняются ли глобальные настройки и авторизация пользователя при
  заданном `OPENCODE_CONFIG_DIR`, и принимает ли `instructions` абсолютный
  путь.
- Claude Code: работает ли `--append-system-prompt-file` в интерактивном
  режиме; иначе передавать текст через `--append-system-prompt`.

Если нативный путь для harness не подтвердился, адаптер использует запасной
путь и сообщает об этом пользователю.

**Запасной путь** (он же — для будущих harness без нативных скиллов): в промт
добавляется короткий каталог «имя — описание» и указание получать содержимое
командой `tbox skill <имя>`. В этой версии запасной путь не реализован: все
три поддержанных harness подключают скиллы нативно, а молчаливый откат на
каталог скрыл бы от пользователя, что нативный путь не сработал, поэтому
неподдержанная версия остаётся ошибкой (см. ниже).

Версия harness проверяется перед запуском. Неподдержанная версия даёт
понятную ошибку с минимальной версией, а не запуск без скиллов.

`tbox clean` удаляет только то, что создал `tbox`: каталоги `run/`, каталог
`plugins/cache/tbox/` и файлы `tbox-*.config.toml` в `$CODEX_HOME`.

## `tbox` внутри сессии

Когда задана `TBOX_IMAGE_DIR`, `tbox` работает в режиме агента:

```
tbox skills                         # скиллы образа: имя и описание
tbox skill <имя>                    # описание, список файлов и SKILL.md
tbox skill exec <имя> <скрипт> [аргументы]
```

- Виден только образ из `TBOX_IMAGE_DIR`. Stores, другие образы, сборка и
  запуск недоступны: команда завершается с ошибкой и объяснением.
- Если каталог из `TBOX_IMAGE_DIR` отсутствует или повреждён, `tbox`
  завершается с ошибкой и не переходит в обычный режим.
- `skill exec` запускает файл внутри каталога скилла. Путь не может выйти за
  каталог скилла. Рабочая директория — текущая; в окружение добавляется
  `TBOX_SKILL_DIR`. Код возврата и потоки скрипта передаются без изменений.
- Имя скилла внутри сессии — без префикса Store (`some-skill`). Форма
  `<store>/<скилл>` действует вне сессии и адресует скилл в Store.

Вне сессии те же команды работают со Stores:

```
tbox skills                 # все скиллы всех Stores: <store>/<скилл>
tbox skill <store>/<скилл>  # описание и SKILL.md
tbox prompts                # все промты всех Stores
tbox prompt <store>/<промт> # текст промта
```

## Конструктор и интерактивный режим

```
tbox image new [<имя>]
```

1. Спросить имя образа.
2. Показать скиллы всех Stores списком с отметками; пользователь выбирает.
3. Показать промты так же; дать создать новый пустой промт.
4. Создать `sources/<имя>/` с `Tariboyfile.yaml` (v3), `instructions.md` и
   собрать образ.

Для скилла из git-Store конструктор пишет `git` (адрес Store), `path` и `ref`
(текущий коммит Store). Для Store-директории — `dir` с абсолютным путём. Для
Store-архива — `url` нельзя, потому что архив содержит много скиллов; такой
скилл копируется в `sources/<имя>/skills/` и записывается как `dir` (решение
автора).

`tbox run` без аргументов: список образов (собранные и из Stores), затем
список установленных harness, затем запуск.

Все интерактивные команды имеют неинтерактивную форму с флагами
(`tbox image new <имя> --skill ... --prompt ...`), чтобы их можно было
тестировать и вызывать из скриптов (решение автора). Без терминала
интерактивная форма завершается с ошибкой и подсказкой.

## Совместимость с tariboy

- В `tbox/testdata/compat/` лежат исходники v2 без плагинов и runtime-вставок
  и ожидаемый digest каждого. Отдельный образец — исходник v3 с плагинами,
  вставками и пометками `only: tariboy`: архив `tbox` из него должен пройти
  импорт в tariboy. Тест `tbox` и тест в `internal/image` собирают
  один и тот же исходник с фиксированными временем сборки и ref и сверяют
  результат с записанным digest. Код друг друга тесты не вызывают.
- Тест в tariboy импортирует архив, собранный `tbox` и сохранённый в
  образцах, через существующую проверку переносимого архива.
- Изменение формата архива в tariboy ломает эти тесты в том же PR.

## Сборка, проверки, документация

- `make build` собирает `bin/tbox`; `make install` ставит его рядом с
  остальными бинарниками.
- `make backend-check` получает шаги для модуля `tbox/`: формат, `go vet`,
  `staticcheck`, пороги сложности и тесты. CI запускает их в существующей
  задаче backend.
- Проверка, что в `tbox/` нет импорта tariboy, — отдельный шаг (решение
  автора).
- Документация: новая страница `docs/docs/binaries/tbox.mdx`; строка в
  `docs/docs/binaries/index.mdx` и в `README.md`; раздел о schema v3 и о том,
  что tariboy её пока не собирает, в `docs/docs/images/index.mdx`.

## Этапы

Каждый этап — отдельный PR и полезен сам по себе.

1. **Ядро.** Модуль `tbox/`; разбор v2 и v3 с локальными `dir` и `file`;
   сборка, хранилище, `export` и `import`; `tbox run` для Claude Code, Codex и
   OpenCode; режим агента (`skills`, `skill`, `skill exec`); `tbox clean`;
   тесты совместимости; сборка и CI.
2. **Источники.** Stores (`store add|list|show|refresh|ref|remove`); записи
   `git` и `url` в v3; кэш и `tbox-lock.json`; чтение `skills-lock.json` для
   v2; `tbox images|skills|prompts` по Stores; `tbox build <store>/<образ>`.
3. **Конструктор и интерактив.** `tbox image new`; `tbox run` без аргументов.

После первого этапа — отдельная задача вне этого документа: поддержка v3 в
tariboy и разметка официальных образов в `tariboy-store`.

## Что остаётся исполнителю

- Раскладка пакетов внутри `tbox/` и выбор библиотек для разбора команд,
  YAML и терминальных списков.
- Точные тексты ошибок и предупреждений, формат вывода списков, флаг `--json`.
- Формат `stores.json` и `tbox-lock.json`.
- Пределы размера и времени для сети и архивов.
- Список мест, где ищется `SKILL.md` в Store без каталога `skills/`.
- Блокировки при одновременных сборках и запусках.

## Известные риски

- Codex меняет систему плагинов быстро. Адаптер зависит от раскладки кэша и
  от профилей; проверка версии и запасной путь ограничивают ущерб.
- Вторая реализация формата может разойтись с tariboy. Тесты совместимости
  покрывают архив; правила разбора v2 покрываются общими образцами исходников.
- Официальные образы остаются v2 без разметки, пока tariboy не понимает v3. До
  этого они запускаются в `tbox` со скиллами, которым нужен демон.
- Срабатывание скиллов зависит от harness и модели. Нативная доставка
  уравнивает `tbox` с обычной установкой скиллов, но не гарантирует вызов.
