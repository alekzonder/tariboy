### Что подтверждено кодом

- `internal/commands/image.go:imageBuild` уже публикует тег из `image_version` вместе с `latest`, если теги не заданы явно. Источник замораживается один раз; публикация архива и provenance защищена общим publication gate и откатом.
- `ui/src/lib/stores.ts:buildStoreImage` уже отправляет только Store selector, поэтому кнопка Build использует именно этот режим.
- `internal/stores/stores.go:builtVersions` выбирает наиболее позднюю сборку среди всех тегов и возвращает **имя тега**. Поэтому Built version и Update needed сейчас не отвечают на вопрос о содержимом latest.
- `imageLs` возвращает name, tag, digest, built_at, но не image_version.
- `BuiltImages.tsx` выводит строку на каждый тег. Просмотр manifest, template и файлов уже существует.
- `agentImageStatusValue` возвращает current/pending ref и digest, а Configuration показывает ссылки без версии.
- `internal/loop/image_activation.go` уже проверяет mutable ref перед запуском, сохраняет новый digest как pending и активирует через существующие staging/bridge/shim/promotion. Явный pending имеет приоритет. Этот вывод основан на чтении кода; проверка конкретного сценария пересборки latest будет закреплена тестом.
- Версия уже сохраняется в snapshot итерации. Одинаковый image_version не означает одинаковые байты.
- Разные теги одной сборки имеют собственные digest, поскольку manifest содержит имя тега. Не будем требовать равенства digest у latest и version-tag.

### Подходы

1. **Рекомендую:** дополнить существующие API метаданными, сгруппировать Images по имени в UI, исправить источник версии Store и показать серверную проекцию следующего запуска. Публикацию и механизм активации переиспользовать.
2. Только группировка и подписи в UI: меньше изменений, но невозможно достоверно показать активный digest и приоритет pending; не покрывает запрос.
3. Новый registry с отдельным каталогом релизов и историей перемещения тегов: больше миграций и дублируемого состояния; для описанной задачи не требуется.

### 1. Images: список образов → теги → содержимое

Первый экран содержит одну строку на имя образа:

| Image | Latest: image_version | Latest built at | Newest built tag | Tag built/updated at |
| --- | --- | --- | --- | --- |
| reviewer | 1.4.0 | дата сборки latest | 1.5.0-rc.1 | дата сборки этого тега |

- Latest означает именно ref `name:latest`, независимо от наличия более нового тега.
- «Самый свежий собранный тег» выбирается по времени сборки, не по SemVer. При одинаковом времени у тегов одной сборки предпочитаем version-tag перед latest; для остальных совпадений используем стабильный порядок по имени.
- В этом плане дата обновления собранного тега означает его `built_at` — время последней сборки содержимого. При импорте старого архива это исходная дата сборки, а не дата импорта. Отдельный журнал перемещения/импорта тегов не добавляется.
- Отсутствующий latest показываем явно; не подменяем его самым свежим тегом. Отсутствующий image_version — «Версия не указана», а не строка latest.
- Клик по имени открывает таблицу всех его тегов: tag, image_version, built_at, digest. Теги latest и наиболее свежий отмечены отдельно.
- Клик по тегу открывает существующий просмотр manifest/template/files. Добавляем хлебные крошки к имени и общему списку, сохраняем существующие прямые URL тегов.
- Export, transfer, remove остаются действиями конкретного тега; import остаётся на общем экране. Сохраняем запрет удаления используемых образов и ограничения reserved/immutable.
- Все запросы и ссылки остаются привязанными к серверу из маршрута; группировка не смешивает хосты.
- Версия и manifest должны относиться к одному digest. Если при просмотре mutable ref изменился, UI должен сообщить об обновлении и загрузить согласованное содержимое; отображение активной версии агента не должно обращаться к текущему latest вместо pinned digest.

Основные места: `internal/commands/image.go`, `ui/src/lib/api.ts`, `ui/src/pages/images/BuiltImages.tsx`, `ui/src/pages/ImagesPage.tsx`, `ui/src/components/ImageLayout.tsx`, существующие маршруты Images. Новый экран тегов — небольшой компонент рядом с BuiltImages, без нового UI-фреймворка.

### 2. Store: сравнение с содержимым latest

- Читать исходный image_version штатным parser из текущего Tariboyfile.yaml.
- Built version получать только из manifest `<image_name>:latest`, поле image_version.
- Update needed означает **несовпадение** двух явно заданных версий, включая ситуацию, когда исходник старше собранного latest. Не заменять это проверкой «SemVer больше».
- Нет latest — статус «Не собран latest», Build доступен, даже если version-tag уже есть.
- Нет версии в исходнике или manifest — отдельный статус «Версия не указана / сравнение недоступно». Не объявлять такой образ актуальным по совпадению двух пустых строк. Старые невёрсионированные исходники по-прежнему собираются только в latest.
- Невалидный исходник блокирует его Build и показывает ошибку; остальные строки остаются доступны. Повреждённый latest также получает явную ошибку, без подмены другим тегом.
- Колонки назвать однозначно: «Source image_version» и «Latest image_version».
- После успешного Build перечитать Store и список Images; сообщение должно подтверждать публикацию version-tag и latest, а не только одного тега.
- Сохранить существующий default build и его атомарность. Не менять поведение явных CLI --tag: это отдельный осознанный режим.
- Сравнение только по версиям не обнаружит изменения файлов без увеличения image_version. Это намеренное соответствие запросу; ручной Build остаётся доступен и при равных версиях.

Основные места: `internal/stores/stores.go`, `ui/src/lib/stores.ts`, `ui/src/pages/StoresPage.tsx`; удалить алгоритм выбора newest tag для Built version, если он больше нигде не нужен.

### 3. Configuration: активный образ и следующий запуск

Расширить существующий `GET /api/agents/{name}/image` аддитивно, сохранив current/pending и существующие команды.

- **Current:** ref, image_version и digest фактически активированного образа. Версию читать по сохранённым ref+digest через pinned inspection. У остановленного агента подпись «Активированная версия», без утверждения, что он сейчас работает.
- **Next iteration:** ref, image_version, digest и причина выбора. Приоритет совпадает с loop: явный pending digest → актуальный digest mutable active ref → текущий pinned образ.
- Mutable latest проверяется для preview и при отсутствии pending. Иначе UI не увидит обновление до границы итерации.
- Это прогноз по состоянию сервера на момент чтения, не резервирование: latest может ещё измениться до запуска.
- Если next digest отличается, показывать «Обновление на следующей итерации», даже при равных image_version.
- Ошибка чтения/активации отображается явно, в том числе когда pending.ref пуст. Не подставлять старую версию как гарантированно следующую.
- Preview — read-only: просмотр Configuration не создаёт pending и не активирует образ.
- Сохраняем приоритет явного pending и существующие Use next iteration / Cancel pending. Отмена явного pending не отключает автоматическое следование mutable ref.
- Обновлять проекцию при штатном refresh состояния агента, после назначения/отмены и события сборки, с защитой от запоздалого ответа другого host/agent.

Основные места: `internal/commands/agents.go`, `ui/src/lib/api.ts`, `ui/src/pages/agents/AgentConfigurationTab.tsx`. Изменения loop — только если тест выявит реальный дефект; новый менеджер обновлений не нужен.

### 4. Проверка перехода на следующей итерации

Добавить детерминированный сценарий со stub/fake harness и изолированными каталогами:

1. Собрать image_version 1.0.0 с latest, создать агента на latest и начать итерацию A.
2. Удерживая A работающей, собрать тот же образ версии 1.1.0 через production build path.
3. Проверить: A продолжает использовать прежние digest, prompt и version; Configuration показывает Current 1.0.0 / Next 1.1.0.
4. Завершить A, запустить B: её snapshot содержит новый digest, image_version 1.1.0 и новый prompt/template.
5. Повторить с изменёнными байтами без изменения image_version: переход всё равно определяется digest.
6. Отдельно покрыть приоритет явного pending, неизменившийся latest, immutable ref и ошибку подготовки нового образа. При ошибке старые активные байты сохраняются, новый запуск не объявляется успешным, ошибка видна оператору.

Переиспользовать `internal/loop/image_activation_test.go` и имеющиеся command/image tests. Не запускать реальных рабочих агентов.

### Критерии приёмки

- Images различает latest и действительно самую свежую сборку и позволяет пройти от имени к тегам и содержимому.
- Store сообщает версию внутри latest и сравнивает её с исходником, а не с именем последнего тега.
- Build версии V публикует V и latest из одной замороженной сборки; ошибка не оставляет частично опубликованный результат.
- Configuration показывает фактическую активную версию и прогноз следующей с digest.
- Работающая итерация не меняется при rebuild; следующая использует новый mutable digest при отсутствии приоритетного pending.
- make check проходит; make full-check не запускается. Версия продукта не повышается.
